# Juniper
*Financial planning app for young individuals and families, partner optional.*

*Last updated: 2026-08-29 (third pass) by kuba-vault*

## TL;DR

Juniper is a financial planning app for young individuals and families: net worth, spending, budgets, a proprietary 0 to 100 Juniper Score, and plans, all built from the member's own linked accounts. It runs at `www.juniperplan.com` on Plaid Production against a real member's real banks: **7 linked Plaid items** across at least six named institutions, reading **about $97k** of net worth. The phase is post-MVP iteration. **One product PR has landed since the last pass, #195, and it fixed the shared space's headline number.** The combined "Together" total read the coarse `share_balances` flag and summed every account a member had, ignoring per-account scope entirely, so since migration 0020 set that flag false a partner contributed exactly 0 however many accounts they shared: sharing an account changed the list and never the number. Totals are now accumulated from the same per-account scopes the rows are built from, in the same pass. The same PR cut the three-way share control down to one switch, because "Balance only" and "Shared" did the same thing. **The twelve PRs before it (#182 to #193) share one subject: how true each number on screen is, and saying so.** A refusing item's balances are now carried forward for at most seven days (#183) instead of being folded into every future total forever; a chronically slow bank answers from Plaid's cached balances instead of not at all (#187, confirmed working in production); every connection on Connections states its own freshness and offers Reconnect through Plaid update mode (#192, #193). **#191 deleted the last seeded data in the repo**, the invented "Maya and Devin" household, which makes the CLAUDE.md rule that only the member's own real data may render true by construction rather than by every page choosing not to import a fixture that was still sitting there. Bills and Activity were de-seeded and routed in #186, so all five shared surfaces are live. **Ops:** migrations 0022 and 0023 are applied, all of 0001 to 0023 are live with no duplicates, and the 09:00 UTC cron fired and returned 200 on 2026-08-29 at 09:01:35, though with `members_due: 0`, so its schedule and auth are proven and its sync work is not. **Two things are explicitly unverified and recorded as such:** #193's update-mode branch has never executed, because it needs a genuinely dead item and all seven connections are healthy, and the Stage 6 compliance pair is still open. Also still open: Plaid's `recurring_transactions` add-on, a Charles Schwab relink, and affiliate URLs still `example.com`. One known limitation was deliberately left unfixed and written into the code beside the arithmetic: an account both members linked separately is counted twice in the combined total.

## What it is

**The problem:** Money is spread across banks, cards, brokerages and loans, and there is no single honest view of where a person stands or what a decision would cost them. The tools that try either invent numbers to fill the gaps or stop at a budget.
**The solution:** A planning app that reads the member's own linked accounts and turns them into a net-worth trend, spending that means consumption rather than every outflow, a 0 to 100 Juniper Score built only from what it can actually measure, and plans funded from real balances. A partner can be invited as an optional layer on top; nothing crosses to them until it is explicitly shared.
**The user:** Individuals and families, late 20s to early 40s. Solo is the default experience, not a fallback.
**The value:** One place that tells a member the truth about their own money, with a next step attached to each number.

*This supersedes the original couples-first framing. The repositioning is Stage 0 in ROADMAP.md ("audience: individual-first, partner as a layer"), and as of #171 to #177 it is built: the personal app is complete on its own, and the shared space is a second workspace you switch into.*

## Where we are right now

**The most recent PR, #195, fixed a number that had been wrong since the shared space shipped.** The combined "Together" total on the shared Overview read `const partnerNW = theirs.share_balances ? await memberNetWorth(partnerId) : 0;`. `memberNetWorth` summed EVERY account a member had and gated the lot on the coarse `share_balances` pref, so per-account scope did not enter the total at all. That is wrong in both directions. Migration 0020 set that flag false on 2026-08-29, so a partner contributed exactly 0 no matter how many accounts they shared, which is why sharing an account moved the list and never the number, and why the control felt hollow. Had the flag been true, the total would have counted accounts the member had explicitly marked private. Totals are now accumulated from the same per-account scopes the rows are built from, in the same pass over the same accounts, so the figure cannot disagree with the list beneath it. `memberNetWorth` had no other caller and was deleted. Both members now see the SAME figure, what each has put into the shared space, rather than each seeing their own full net worth plus the other's shared portion. Verified over five cases including the two that were broken: "both share one" went from 0 to 3000, and an explicit private beat a true coarse flag, 2300 rather than 300.

**Sharing an account is one choice now, not three** (#195). The sheet offered Private / Balance only / Shared, and the last two did the same thing: both exposed the account and its balance, and neither withheld transactions, because transactions are not shared at all. The only difference in the code was a label on the `owner` field (`owner: scope === "shared" ? "shared" : "you"`), so a three-way control was drawing a distinction the data did not make. It is one switch per account now, with a single sentence under the list saying what sharing exposes (name, balance, and a contribution to the total together) and what it does not (transactions). `AccountScope` in `lib/partner.ts` still reads `"balance"` for rows written before the change and `isShared` treats it as shared; only `"shared"` and `"private"` are written (`WritableScope`). No migration was needed. `pages/app/shared/accounts.tsx` was brought in line, its three-state chip cycle replaced by the same toggle.

**One limitation was recorded rather than fixed:** an account BOTH members linked separately is counted twice in the combined total, once on each side. That is now a comment beside the arithmetic in `api/partner.ts` instead of only in conversation. Fixing it needs a per-account "joint" designation, and that has to be a member's decision, because two accounts at one bank with the same balance are not necessarily the same account. Finley's framing, worth keeping: most individuals will never need the option, but anyone with genuinely shared accounts certainly will, so it should probably be something Juniper NOTICES and asks about once (same institution, same mask, both shared) rather than a field every member fills in for every account. It is also not only arithmetic: a joint account should read as "ours" rather than as "yours" sitting in a shared list, which is what the existing `owner: "shared"` field was reaching for with nothing behind it.

**The twelve PRs before that (#182 to #193) are all one subject: how old a number is, and whether the screen says so.** #180 had let a refusing item contribute its last known balances so the day's trend point survived. #183 puts a ceiling on that at seven days, because an item that never comes back would otherwise fold a frozen number into every future total, presented as today's, with the only signal a dashed point indistinguishable from a legitimately reconstructed one. Dating the carry needed a new column, `balances_refreshed_at` (migration 0022), because neither timestamp already on `plaid_items` answers "how old are these balances": `last_synced_at` is set by transactions-sync too, and the problem item syncs transactions fine while every balance call times out, so it looks freshly synced forever; `updated_at` is trigger-maintained and moves on any write, including the cursor.

**That problem item has a name, and it now answers.** Item `5vyavBky` is **Carter Bank & Trust**, the member's primary checking, and `/accounts/balance/get` times out on every attempt, at 9s and then at 12s. #187 falls back to `/accounts/get` on a timeout only, never on a dead item or a permissions error, which are real answers that must not be papered over with cached figures. `/accounts/get` returns the balance Plaid already holds with no round trip to the bank, so it answers in about a second and is still Plaid's number rather than a copy of ours from days ago. The fallback is budgeted from the remaining run time rather than from the call that just timed out. It writes `balances_refreshed_at`, which also stops #183's ceiling from dropping Carter out of net worth around September 5. **Confirmed working in production**, log line `used Plaid's cached balances from /accounts/get instead`. Treat Carter as permanently on the cached path: one of the seven balances is not a live read, and that is a known state rather than a bug.

**Connections now says all of this out loud** (#192). Every fact was already recorded and never asked for: `last_synced_at` and `last_error_code` since 0017, `balances_refreshed_at` since 0022. A healthy connection reads "Updated 4 minutes ago", a finished one reads "Needs reconnecting", and a cached balance says so. That last state needed migration 0023 (`balances_from_cache`), because #187's fallback writes `balances_refreshed_at` exactly like a live pull, deliberately, so nothing on the row distinguished them. `api/plaid/accounts.ts` asks for the health columns and retries without them if the select fails, since PostgREST rejects a whole select on one unknown column.

**The Reconnect button is real, and its risky half is the return trip** (#193). Reopening Link for the same bank the obvious way creates a *second* item and leaves the dead one behind with its stale balances. Update mode passes the item's `access_token` instead of `products`, which repairs the item in place. The trap is that Link still hands back a public token on success, and exchanging it mints exactly the duplicate the whole feature exists to avoid, so `onSuccess` reads the repair flag from the queue rather than from Plaid's metadata and returns before the exchange. **This branch has never executed.** It needs a genuinely dead item and all seven connections are healthy. It was checked by reading and by a structural assertion that the exchange sits after the update-mode return, not by running it.

**The last seeded data in the app is gone** (#191). `lib/shared-data.ts` and `pages/app/shared/sharing.tsx`, 143 lines, held the invented couple "Maya and Devin" with their accounts, bills, goals and conversation. `sharing.tsx` was its only importer, unrouted since Stage 4c and superseded by the share sheet. The CLAUDE.md rule that only the member's own real data may render is now true by construction, not by every page choosing not to use a fixture that was still there.

**Bills and Activity joined the nav** (#186), de-seeded and routed like Accounts and Goals before them, so all five shared surfaces are live. Presence of bills and messages is decided server-side and rides on `/api/partner`, so the app bar needs one call rather than three. It also fixed a reachability bug worth naming: `SharedPage` replaced the children of *every* shared page with the blank canvas while the space was empty, so a member following the canvas to Bills was shown the canvas again and could never add a first bill. The canvas belongs to the shared Overview alone now, each sub-page carries its own empty state, and the canvas grew to four tiles.

**Signup goals look like the plans they are about to become** (#184). They render as unstarted cards at plan size on Plans, and as rows in the Overview "Your plans" card, instead of a chip strip under an empty state that claimed nothing existed. The 2026-08-26 decision is unchanged: no plan row is written until the member sets a target, and every figure on an unstarted card reads "Not set" rather than a zero. Both surfaces read one helper, `unplannedGoals` in `lib/plans`, which is why `GOAL_ROUTES` and `isAlreadyPlanned` moved there. #185 then fixed my own bug in it: the Plans page has an outer `views.length === 0` branch that returns the big "No plans yet" card before reaching the grid, so the one member the feature was for could not see it at all. #185 also closed a flash where plans resolved before the profile did.

**Two self-inflicted layout bugs on the Overview transactions card, and one lesson** (#188, #189). #181 had capped the list at 520px, but the card sits in a two-column grid beside Accounts and grid children stretch, so the card was already about 995px and the cap left a scrollbar with roughly 450px of dead space beneath it. #188 made the list fill the card. #189 then removed the inner scroll entirely, because `overscroll-behavior: contain` trapped the wheel whenever the cursor was over the card. Both were mine, and the shared cause is in Notable debug lessons: #188's harness used short merchant names, measured no overflow, and certified a layout that could not overflow.

**Plan cards can be opened from the keyboard** (#190). The card was a div with `onClick`, no role, no tabindex and no label, and its only affordance was a span at opacity 0 revealed on hover. The card is deliberately *not* a button, because it contains one (Ask Juniper) and nesting interactive content inside a button is invalid, so the footer hint became a real labelled button per plan. The unstarted cards from #184 had the opposite problem, a tabindex on a div with a button inside it, and got the same treatment.

**Ops state.** Migrations 0022 and 0023 were applied to production on 2026-08-29; all of 0001 to 0023 are applied, with no duplicate numbers. `CRON_SECRET` is set, and the 09:00 UTC scheduled run fired and returned 200 on 2026-08-29 at 09:01:35, reporting `members_due: 0` because the member had synced inside the 20-hour window. So the cron's schedule and auth are proven and the cron doing real sync work is still unexercised.

**Still open, and not re-litigated:** the Stage 6 compliance pair (financial-data TOS and privacy policy, security review of the data surfaces) before broad public linking; the Charles Schwab relink, without which the reconstructed net-worth trend is flat across about 73% of net worth; Plaid's `recurring_transactions` add-on, still pending on Plaid's side, so every recurring-sync logs one warning and returns `available: false`; and affiliate URLs still `example.com` pending licensing. Per-account scope never entered the number, so after migration 0020 closed that flag the partner contributed exactly 0 whatever they shared, and had the flag been true the total would have counted accounts explicitly marked private. `youNW` and `partnerNW` are now accumulated inside the same loops that build the account rows, one skip rule for both, so the figure cannot disagree with the list under it, and `memberNetWorth` was deleted with no other caller. **Both members see the same figure**, what each has put into the shared space; summing the caller's own accounts in full would have given the two of them different totals for one shared page. The coarse `share_balances` pref survives in exactly one job, as the default in `scopeFor` for an account with no `account_shares` row, which since 0020 means private. `set-account-share` writes `"shared"` or `"private"` and still accepts `"balance"` for rows that predate #195. **Known and deliberately unfixed, recorded as a comment beside the arithmetic:** an account both members linked separately is counted twice, once on each side, so this total is "what the two of you have put in", not "what the two of you are worth"
- **A daily cron, so a member who never opens the app still has a history** *(PR #167, `api/cron/daily-sync.ts`)*: `net_worth_snapshots` and `score_history` are keyed by (user, day), so a day nobody wrote is a day nobody can write later, and until this landed the only trigger was a member opening the dashboard. The awkward part is that the three sync endpoints authenticate a member's JWT and a cron holds none. Rather than teach three member-facing endpoints a second way to be trusted, each was split at the point the user id is known: a handler that establishes the caller, and a `run*(userId)` that does the work. The cron calls those, so a scheduled refresh and a member-triggered one are the same code. It refuses anything without `Authorization: Bearer $CRON_SECRET`, compared in constant time, and refuses everyone including Vercel when that variable is unset. Members stale past 20 hours are served stalest first, to an 18s deadline, and it will not start a member it cannot finish. Scheduled `0 9 * * *` in `vercel.json`
- **Backfill merchant art without replaying the sync cursor** *(PR #178, `api/plaid/merchant-art-backfill.ts`)*: `/transactions/sync` is incremental by cursor and never revisits a stored row, so #158's art only worked forward. This fills `merchant_logos` from `/transactions/get` over a 180-day window, leaving sync state alone, and `api/transactions.ts` resolves a row as `t.logo_url ?? logoOf.get(t.merchant_name)`, so one merchant-level upsert covers a whole history. It asks the database which merchants are missing first and returns without calling Plaid when none are, which is what makes it safe on every refresh and from the cron
- **One refusing bank costs its own balance, not the day, and not forever** *(PRs #180, #183, #187, `api/plaid/networth-snapshot.ts`)*: an item that fails now contributes its last known balances from the stored `plaid_items.accounts` snapshot and the row is written with `estimated = true`, rather than the whole day's trend point being dropped. Skipping survives only for an item that has never refreshed at all, where there is no last known balance to carry. The run also reserves `WRITE_RESERVE_MS` (4s) of its 18s deadline for the tail after the Plaid call, since `refreshItem` is a Plaid call plus two Supabase writes and only the call had been inside the budget, which is why the function was still being killed at 25s. **#183 put a ceiling on the carry at seven days** (`CARRY_MAX_DAYS`), because an item that never comes back would otherwise fold a frozen number into every future total, presented as today's, and the only signal would be a dashed point indistinguishable from a legitimate reconstruction; past the cutoff the item stops contributing and the day is skipped honestly, which is what the original rule protected. An item that never refreshed and one whose balances went stale are counted apart in the log, and `carry_expired` rides on the response so a trend that stops receiving points explains itself outside the logs. **#187 then made the slow bank answer at all:** on a timeout only, never on a dead item or a permissions error, the endpoint falls back to `/accounts/get`, which returns the balance Plaid already holds with no round trip to the bank, in about a second. The fallback is budgeted from the run's remaining time rather than the budget of the call that just timed out. `balances_refreshed_at` (0022) is written here and nowhere else, beside the snapshot it dates, and `balances_from_cache` (0023) records which of the two paths wrote it
- **Plaid calls have deadlines, and the pool has no barrier** *(PRs #152, #162, `api/_pool.ts`)*: a member with twelve institutions was getting a 504 on `/api/plaid/networth-snapshot`, because the loop was serial and `/accounts/balance/get` goes to the bank for a live balance, so its latency is the bank's. #152 batched six at a time; #162 finished the job, because a batch is a barrier and one twenty-second bank parked five idle workers. `mapPool` is six workers pulling from one cursor, pure and importing nothing. - **Spending means consumption, and every category means something** *(PR #136, `api/_categorize.ts`)*: `/api/finances` used to read only the sign of a transaction amount, so every outflow was spending and every inflow was income. A transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent, and the card payment was the worst of it, because the purchases behind it already counted when they happened, so the member was billed twice in the same month. `_categorize.ts` is now the single taxonomy table: **11 groups** (9 spend, 1 income, 1 transfer) over **46 leaf categories**, driven by Plaid's *detailed* `personal_finance_category` with the primary as a floor. Each group carries a `kind`, and three rules follow from it: `transfer` is ignored entirely, `income` is netted from its own categories, and `spend` is summed **signed**, so a refund reduces the category it came back to instead of masquerading as income. Groups are derived at read time and never stored, and `spent` is *defined as* the sum of the breakdown, so the card header, the donut center, and the cashflow strip cannot disagree. The same three rules run in `api/_finance-snapshot.ts`, which is why this reaches past the dashboard: those two numbers feed the Juniper Score's savings rate and emergency-fund factor. The pure arithmetic lives in `api/_networth-walk.ts`, split out following the `_score.ts` convention, because the signs are the whole correctness story. Investments cannot be reconstructed exactly (market movement is not a transaction and Plaid has no historical price feed), so the invested balance is today's holdings minus net contributions since, read from `/investments/transactions/get`. ## Decisions log

- **2026-08-29, the combined total is accumulated from the same per-account scopes as the list it sits above** - the total read the coarse `share_balances` flag and summed every account the member had, which was wrong in both directions: migration 0020 set that flag false, so a partner contributed exactly 0 however many accounts they shared, and had it been true the total would have counted accounts explicitly marked private. `youNW` and `partnerNW` are now added up inside the same pass that builds the rows, so the number cannot disagree with what is drawn beneath it, and `memberNetWorth` was deleted rather than repaired. Rejected: summing the caller's own accounts in full and adding the partner's shared portion, which reads naturally for one person and gives the two members different totals for one shared page. Both now see the same figure, what each has put into the shared space. Verified over five cases, including the two that were broken: "both share one" went 0 to 3000, and an explicit private beat a true coarse flag, 2300 rather than 300.
- **2026-08-29, sharing an account is one switch, because the three-way control drew a distinction the data did not** - "Balance only" and "Shared" both exposed the account and its balance, and neither withheld transactions, because transactions are not shared at all; the only difference in the code was a label on the `owner` field. A member was therefore being asked to weigh a choice with nothing behind it. One sentence under the list now states what sharing exposes and what it does not, said once instead of as a help line on each row, because "what does this NOT show them" is the actual question. Rejected: making "Balance only" real by withholding something, which would have meant building transaction sharing first in order to withhold it. `AccountScope` still reads `"balance"` for older rows and `isShared` treats it as shared, so no migration was needed.
- **2026-08-29, an account both members linked separately is knowingly counted twice, and the fix waits for a member's decision** - the combined total adds each side's shared accounts, so one joint account linked from two logins appears on both. Fixing it needs a per-account "joint" designation, which cannot be inferred: two accounts at one bank with the same balance are not necessarily the same account. The limitation is written into `api/partner.ts` beside the arithmetic rather than left in conversation, so the number is not trusted further than it deserves. The likely shape when it is built is a prompt rather than a field, something Juniper notices once (same institution, same mask, both shared) and asks about, because most individuals will never need the option and anyone with genuinely shared accounts certainly will. It is not only arithmetic either: a joint account should read as "ours" rather than as "yours" in a shared list, which is what the existing `owner: "shared"` value was reaching for with nothing behind it.
- **2026-08-29, Reconnect uses Plaid update mode, and returns before the token exchange** - the obvious repair, reopening Link for the same bank, is actively harmful: it mints a SECOND item and leaves the dead one in place with its stale balances still feeding net worth. Update mode passes the item's `access_token` instead of `products` (Plaid rejects `products` in update mode, since the item already has them) and repairs the item where it stands. The non-obvious half is the return trip: Link still hands back a public token on success, and exchanging it creates exactly the duplicate the feature exists to prevent, so `onSuccess` reads the repair flag from the queue rather than from Plaid's metadata and returns before the exchange. Rejected: reading the flag off Link's own metadata, which would put the decision in the least trustworthy place in the flow. **Never executed:** the branch needs a genuinely dead item and all seven connections are healthy, so it is verified by reading and by a structural assertion that the exchange sits after the update-mode return, not by running it.
- **2026-08-29, a cached balance is recorded as such rather than presented as a live one** - #187's fallback writes `balances_refreshed_at` exactly like a live pull, deliberately, because the balance really was refreshed from Plaid. That left nothing on the row to distinguish the two, and Connections would have shown Carter Bank & Trust as identical to the six institutions answering live. Migration 0023 adds `balances_from_cache`, written on every refresh so it always describes the most recent one. Rejected: leaving `balances_refreshed_at` unset on the cached path, which would have been simpler and would have re-armed #183's seven-day ceiling against the one item the fallback exists to keep in the total.
- **2026-08-29, a slow bank falls back to Plaid's cached balances, on a timeout and nothing else** - `/accounts/balance/get` asks Plaid to go to the bank right now, which is exactly what a chronically slow bank cannot do inside any sane budget; `/accounts/get` returns the balance Plaid already holds, in about a second, and is still Plaid's number rather than a copy of ours from days ago. The fallback is taken **only** on `JUNIPER_REQUEST_TIMEOUT`. A dead item, a permissions error and a relink prompt are real answers about the member's data and must not be papered over with cached figures. Budgeted from the run's remaining time, not from the budget of the call that just timed out, so a 12s timeout cannot be followed by a full second attempt.
- **2026-08-29, a failing item's balances are carried forward for at most seven days** - #180 kept the day's trend point alive by letting a refusing item contribute its last known balances. That had no answer for an item that never comes back: its frozen number would be folded into every future total, presented as today's. Past `CARRY_MAX_DAYS` (7) the item stops contributing and the day is skipped honestly again, which is what the pre-#180 rule was protecting. Dating the carry needed a new column, `balances_refreshed_at` (0022), because `last_synced_at` is set by transactions-sync too (and the problem item syncs transactions fine while every balance call times out, so it looks freshly synced forever) and `updated_at` is trigger-maintained on any write to the row. Rejected: reusing either existing timestamp, which would have made the ceiling silently never fire.
- **2026-08-29, the seeded household is deleted rather than left unrouted** - `lib/shared-data.ts` and `pages/app/shared/sharing.tsx`, 143 lines, held the invented couple "Maya and Devin" with their accounts, bills, goals and conversation. Once #186 de-seeded Bills and Activity, `sharing.tsx` was the fixture's only importer, itself unrouted since Stage 4c and superseded by the share sheet. Deleting both makes the CLAUDE.md rule that only the member's own real data may render true **by construction** rather than by every page choosing not to import something that is still sitting there. Rejected: keeping the file for reference, which is how a fixture ends up back on a screen.
- **2026-08-29, a plan card stays a div and grows a real button inside it** - the card needs to be openable from the keyboard, and the obvious fix, `role="button"` plus `tabindex`, is invalid here because the card already contains a button (Ask Juniper) and interactive content nested inside a button announces badly. So the invisible hover hint became a real, per-plan labelled button, and the card's own click stays a mouse shortcut on top of it. Rejected: making the hover hint focusable where it stands, since a control that takes focus while invisible is worse than one that never takes focus at all.
- **2026-08-29, an unstarted signup goal is drawn at plan size, and still writes no row** - the 2026-08-26 decision that a signup goal is an offer rather than a plan row is unchanged: nothing is written until the member sets a target, because the alternatives are inventing a zero target or leaving an orphan when they back out. What changed is only where the goal sits and how large it is. It renders as a dashed card in the Plans grid and as a row in Overview's "Your plans" card, with every money figure reading "Not set". Rejected: writing a placeholder plan on signup, which is the same decision rejected for the same reason a fortnight earlier.
- **2026-08-29, presence of shared content is decided server-side and rides on `/api/partner`** - the app bar's shared tabs grow as content lands, which means the bar has to know whether bills and messages exist. Asking each surface would be three calls on every app load. `/api/partner` already answers once for the workspace, so `holds` carries bills and activity alongside accounts and goals, and the bar, the canvas and the pages cannot hold different answers about what the space contains.

- **2026-08-29, sharing is private by default, and one sheet is the only thing that shares** - `partner_sharing_prefs.share_balances` shipped `DEFAULT TRUE` in migration 0012, `DEFAULT_PREFS` in `api/partner.ts` carried the same default, and `scopeFor` fell back to `"balance"`, so accepting an invite exposed every one of the inviter's accounts at balance level with nobody being asked, while the invite modal promised in writing that accounts, net worth and spending stay private. Migration 0020 makes both moves in the revoking direction: the column default becomes FALSE, and every existing row is set FALSE, closing the exposure on partnerships already formed. Re-sharing is deliberate and per account, through `components/juniper/share-sheet.tsx`, which writes `account_shares` rows and is unaffected by the flip. Rejected: leaving the default and adding a warning, which would have kept the app's behaviour and its own copy contradicting each other.
- **2026-08-29, the shared space starts as an empty canvas and grows what the two of you put on it** - "option D" of the shared-workspace treatments. The nav is derived from content rather than declared: Overview is always there, Accounts appears once either member has shared an account, Goals once a goal exists, so a tab never opens onto an empty surface. Bills and Activity are deliberately left out because their pages still read `lib/shared-data.ts`, and a tab onto a seeded household is exactly what Stage 4c unrouted them for. `pages/app/shared/sharing.tsx` is superseded rather than pending: per-account scope is the grain people actually think in, so its coarse toggles can stay unrouted for good.
- **2026-08-29, switching workspace switches the whole product, not one screen** - the shared tabs live in the app bar itself (`sharedNav` in `app-frame.tsx`), replacing the personal tabs, rather than appearing as a second nav underneath a personal one. What the shared space holds is derived once in `WorkspaceProvider` and read from context, not from a second `usePartner()` call, because `usePartner` is a plain hook: two calls would hold two copies, and sharing an account would grow one nav and not the other.
- **2026-08-29, the partner invite page waits for a session instead of posting immediately, and its handoff param is `?partner=`** - the invited partner is signed out by definition, so accepting cannot be the first thing that page does; `authed()` returned null with no token and `post()` rendered that as "Couldn't join / Please sign in." It now waits for the session, then either accepts or hands off to sign-up or sign-in carrying the token. The param is deliberately not `?invite=`, which the older plan-invite flow already owns on those same two pages, and one page owning two meanings for one param is how a plan invite would silently accept a partnership.
- **2026-08-29, a bank that refuses costs its own accuracy, not the whole day** - `networth-snapshot` used to skip the day's trend point whenever any item failed, on the reasoning that a partial total is a wrong point and a wrong point outlives the outage. A refusing item now contributes its last known balances from the stored `plaid_items` snapshot and the row is written with `estimated = true`, which is the same flag the backfill uses, because both mean the point was worked out rather than read live. Skipping survives only where there is nothing to carry, an item that has never refreshed at all. The chart legend changed from "Rebuilt from your transactions" to "Estimated" in the same PR, because one label can no longer name both causes. Migration 0021 records that widened meaning as a column comment and changes nothing.
- **2026-08-29, merchant art is backfilled through the merchant cache, never by replaying the sync cursor** - `/transactions/sync` is incremental and never revisits a stored row, so art added later reaches only future charges. The obvious fix, nulling `transactions_cursor` to replay history, would re-download and re-upsert years of rows through an edge function with a 25 second ceiling, which migration 0018 explicitly ruled out. `merchant-art-backfill.ts` reads `/transactions/get` over a date window instead, writes only `merchant_logos`, and leaves sync state untouched: one small upsert fixes every past row for that merchant, because `api/transactions.ts` resolves a row as `t.logo_url ?? logoOf.get(t.merchant_name)`.
- **2026-08-28, Plaid is the candidate generator for recurring charges and Juniper owns the confirmation layer** - Plaid has nowhere to store a member's correction (`is_user_modified` is deprecated and modifying streams is discontinued), so anything sent upstream would be lost on the next detection run. Migration 0016 splits the two: `recurring_streams` is a cache overwritten on every sync holding no member intent, `recurring_overrides` is the member's own layer keyed by `stream_id` and reapplied on every read, and a revert deletes the override row because "no row" is exactly the not-yet-reviewed state. Nothing counts toward the total until the member confirms it: Rocket Money auto-commits detections and sweeps them to Inactive after one missed month, and the reported result is a member surprised by a bill that was never flagged. Monarch quarantines instead, and this follows Monarch.
- **2026-08-28, an entitlement refusal is a fact about the account, so the recurring sync returns before it can delete anything** - `recurring_transactions` is a separate Plaid add-on and every production item refused with `INVALID_PRODUCT`. The dangerous path was not the noise, it was falling through: the endpoint deletes streams Plaid no longer returns, so an unentitled run producing zero rows would read as "Plaid no longer detects any of your streams" and wipe the member's cached list on the strength of a permissions error. It now returns 200 with `available: false` before both the upsert and the delete, and writes one warning instead of one error per institution. When the entitlement lands, add it to `additional_consented_products` then and not before, since naming an unentitled product there breaks link-token creation for everyone.
- **2026-08-28, freshness is a server answer, and the manual refresh button is not a member's job** - a member pressing Refresh was doing work the app should do, and in the one case where pressing it felt necessary, a connection whose Plaid login had expired, it could not help, because only a relink fixes a dead token. `/api/finances` now reports when the member's **stalest** connection last synced, stalest rather than newest because newest would call a dashboard current while eleven of twelve banks last answered a week ago. Server-side rather than a local timestamp, because two devices would each keep their own and two tabs would race. The button survives only behind the developer role, carrying a dev badge so it never reads as something a member is expected to press.
- **2026-08-28, the cron gets its own secret and calls `run*()` functions, rather than a second trust path on three member endpoints** - the sync endpoints authenticate a member's JWT and a cron has none. Teaching each one a shared-secret bypass would put a bypass on three member-facing endpoints and spread the trust rule across three files. Each is instead split at the moment the user id is known, into a handler and a `run*(userId)`, so the scheduled refresh and the member-triggered one are the same code and cannot drift. With `CRON_SECRET` unset the endpoint refuses everyone including Vercel, because an unauthenticated endpoint that syncs arbitrary members on demand is worse than a cron that has not been switched on yet.
- **2026-08-28, developer tools sit behind their own role, separate from admin** - `isDeveloperEmail()` reads `DEVELOPER_EMAILS` and falls back to `ADMIN_EMAILS`. The two answer different questions: admin gates the marketplace moderation queue, which is about other people's submissions, while developer gates controls that only ever act on the caller's own account. One person is currently both, which the fallback reflects without welding them together. Worth being precise about what the gate is: every endpoint behind these controls is already JWT-scoped to the caller, so it hides clutter rather than protecting data.
- **2026-08-28, password recovery is two routes built like the front door, and never says whether an address has an account** - treatment B of three; A flipped the sign-in card in place and C used a magic link that signs the member straight in, which would have made recovery a second way into the app rather than a password form. `/auth/forgot` says the same thing either way, because Supabase's endpoint answers identically and a page that said "no account with that email" would turn the form into a way to test whether a given person banks with Juniper. `/auth/reset` waits for the recovery session rather than reading it once, and its three-second timeout only ever downgrades a page still waiting, because telling someone their link is dead while holding a live session for them is the one outcome here with no way back.
- **2026-08-28, Connections is a nav tab, not an account-menu item** - the account menu is for the member's Juniper account, and Connections is a surface about their money. Treatment A of three. B renamed it "Accounts" with the linked count as a badge, which is the better word but renames a page under testers already using it; C made the existing "12 linked" pill the button, which fails on a phone and for a brand new member, because `juniper.css` hides that pill below 720px and it only renders once something is linked. The menu item was removed rather than kept alongside, since two entry points make the tab look like a different destination.
- **2026-08-28, an unmeasured score factor is named rather than silently absent** - #146 made the arithmetic honest by dropping a factor it could not measure and renormalizing the weights, and on its own that is silent: a member cannot tell a part of their financial life Juniper judged fine from one it never saw. Each missing factor now gets a row with "not counted", an empty dashed rail, what Juniper reads it from, and a link to Connections, derived by difference from `score.factors` rather than by having the engine emit placeholders, which keeps #146 intact. No row names points it would add, because connecting an account can just as easily lower the score as raise it, and promising points would be the same shape of claim the flat-70 credit factor was making.

- **2026-08-28, score-factor targets are computed in the engine, not on the page** - `FactorGauge` hangs off `Factor` in `api/_score.ts` (mirrored in `src/lib/score.ts`), so each target sits next to the formula it comes from: 20% of income beside the savings-rate calculation, six months of spending beside the emergency-fund calculation, 0.3x annual income beside the debt calculation, one year of income beside the investing calculation, 30% beside the utilization calculation. A page that recomputed them would be a second definition of the same thresholds, free to drift from the scoring. `gauge` is `null` where a target cannot honestly be stated: with no income there is no savings target, and for a bureau credit score there is no target at all, because naming a "good score" threshold is exactly the kind of invention #146 removed.
- **2026-08-28, reconstructed net-worth points are marked `estimated` and drawn dashed, not presented as observations** - the backfill is honest arithmetic on real transactions, but the invested portion carries no market movement (Plaid has no historical price feed, and `/investments/transactions` returns flows, not prices). Migration `0015_networth_estimated` adds the flag, `/api/finances` returns it per point, and `NetWorthChart` splits the line so the member can see which part of their own history was reconstructed. Rejected: presenting both kinds of point identically, which would have made a reconstruction look like a measurement. Backfilled rows are written with `resolution=ignore-duplicates`, so a day Juniper actually recorded always wins over a reconstruction of the same day.
- **2026-08-27, the credit-score question is answered: VantageScore 3.0, and it is not a licensing problem** - per `docs/CREDIT_PROVIDER.md` (PR #137). FICO Score Open Access does not apply to Juniper twice over: it is a fee waiver for lenders already buying scores, and its counselling track requires a 501(c)(3) or a government agency. VantageScore 3.0 is the route: consumer disclosure is an enumerated permitted use in the base agreement, the trademark licence is royalty-free, and bureau pricing fell to roughly $1 per pull in late 2025. Free to the end user is therefore a margin decision, not a licensing one, and **compliance dominates the cost**, not the score. Treat this as settled: do not re-research it.
- **2026-08-26, the Score page keeps one table of what counts as a plan for each factor** - `FACTOR_ROUTES` in `pages/app/score.tsx` gives every factor a match half (which plan shape, plus a word list) and an offer half (which template to create, or Ask Juniper). Matching reuses `planShape()` so a legacy row with no stored shape is classified the same way it is everywhere else, and completed plans are skipped. The word lists are deliberately narrower than the app-wide `SHAPE_KEYWORDS`, because "fund" alone would let a baby fund answer for an emergency fund. Savings rate matches nothing on purpose: a rate has nothing to save toward, nothing to buy, and no balance to clear, so all three shapes are fictions for it. Rejected: the previous behavior, which rendered `Work on "{plan.t}"` from a seeded demo plan's title, color, and icon, so the number was the member's and the next step was somebody else's.
- **2026-08-26, the demo household is deleted from the client seam, not gated** - `lib/finances.ts` documented three layers, live then manual then mock, and the whole-layer fallback survived every earlier attempt to fence it off, so a member with no profile still saw the demo household's $67,330. `MOCK` is gone, `FinanceSource` is `"manual" | "live"`, and a member with nothing gets the empty layer. ## Risks & known issues

- **Sharing was open by default until 2026-08-29, and that window is not hypothetical.** Migration 0020 closed every existing `partner_sharing_prefs` row as well as the column default, so nothing is exposed now, and since #195 that coarse flag no longer decides anything except the default scope for an account with no `account_shares` row, but any partnership formed before that date had the inviter's account balances visible to the partner from the moment they accepted, with no consent step. It is recorded here rather than only in the Decisions log because it is the kind of thing that has to be findable later.
- **The combined "Together" total double-counts an account both members linked separately.** Known, deliberate, and written into `api/partner.ts` beside the arithmetic. The number means "what the two of you have put into the shared space", not "what the two of you are worth", and it will read high for any couple with a genuinely joint account each of them has linked from their own login. Fixing it needs a per-account joint designation, which is an open loop.
- **The cron has fired but has never synced anything.** The 09:00 UTC run returned 200 on 2026-08-29 at 09:01:35 with `members_due: 0`, because the member had synced inside the 20-hour staleness window. Schedule and auth are proven; the code path that actually refreshes a stale member on a schedule is still unexercised in production. The failure mode is quiet: the job times out or errors and the only symptom is a gap in `net_worth_snapshots` that can never be filled afterwards, because the table is keyed by (user, day).
- **#193's update-mode Reconnect has never executed.** All seven connections are healthy, so the branch that repairs a dead item in place, rather than minting a duplicate beside it, has only been checked by reading and by a structural assertion that the token exchange sits after the update-mode return. If it is wrong the symptom is the exact thing it was built to prevent: two items for one bank, the dead one still feeding stale balances into net worth.
- **One of the seven balances is not a live read, permanently.** Item `5vyavBky` is **Carter Bank & Trust**, the member's primary checking, and `/accounts/balance/get` times out on every attempt, at 9s and then at 12s. #187 falls back to `/accounts/get`, so the figure is Plaid's own cached balance rather than nothing and rather than a stale copy of ours, and #192 says so on the Connections row. This is a known state, not a bug, but it should not be mistaken for a fix: Juniper cannot see a Carter balance newer than whatever Plaid last managed to fetch from the bank, and the underlying slowness is Carter's, not something the app can address.
- **Three different numbers describe "how much is connected", and they are easy to confuse.** Items (7, from the Plaid logs) are what Plaid bills and caps at 200. Institutions (at least six named) is what a member would say out loud, and is not derivable from the logs, because several accounts can sit behind one item. Accounts (13, the app bar pill) is what `linkedCount` sums. Quote items where the evidence is a log line, and never present the pill as an institution count.
- **Every Chase transaction row shows PENDING, including rows several days old.** Unverified. It may be Chase settling slowly, or it may be that stale pending rows are not being reconciled. Listed as a watch item, not a diagnosis.
- **The reconstructed net-worth trend is flat across about 73% of net worth** until Charles Schwab is relinked, because that item never consented to Investments and cannot serve `/investments/transactions/get`.
- **There is no seeded data left in the app** (#186, #191), which closes this risk rather than moving it: `lib/shared-data.ts` and `sharing.tsx` are deleted, and all five shared surfaces read live endpoints. Recorded here because the rule is easy to re-break: a fixture added "just for a screenshot" would put a stranger's invented balances back on a money screen.
- **One surface and one whole shell are kept but unreachable** - Recommended is unrouted (#142), and nothing imports `pages/app-shell.tsx`, so the plan-detail surface and everything hanging off it (marketplace list, affiliate cards, projection charts, debt-list builder, next-action links, portfolio summary, the tap-first dialogue UI) is dead code that still typechecks and still builds. Deliberate and reversible, with un-hide conditions in each header comment.
- **Accessibility has been fixed on one surface, not audited across the app.** #190 gave plan cards and unstarted goal cards a real labelled button, which closes the specific defect logged last run. No sweep has been done over Overview, Transactions, Score, Credit, Connections, Ask or the shared surfaces, so the same pattern (a clickable div with a hover-only affordance) may well exist elsewhere.
- **Ask Juniper streams financial guidance with no safety pass and no disclaimers.** The surface is routed and grounded in the member's real figures. The prompt safety review and the financial-advice disclaimers named alongside it in Stage 11 have not been done.
- **The Credit page reads outside the finances seam** - a documented exception to the `CLAUDE.md` money-data-layer rule, not an oversight: `/api/finances` returns name, institution and balance per account, and utilization needs each card's `limit` from the stored Plaid snapshot. One surface therefore has its own data path.
- **Partner URLs, logos, and rates are demo placeholders** - every affiliate `url` is `example.com`, logos come from a favicon service, and projection rates are fixed constants. Regulated categories likely need specific disclosures and licensing. Do not launch monetized surfaces on these; they are plumbing and UX only.
- **Anthropic cost is uncapped** - no spending limit configured. Per-plan spend is low (structured steps make no LLM call), but Ask Juniper is an open-ended chat surface now, so a runaway loop or abuse could spike.
- **Plaid talks to real banks in production** - linked accounts are real people's real balances, held as an `access_token` in the server-only `plaid_items` table. Three live constraints: the tier caps Items at 200 per product, the Stage 6 compliance pair is not done so linking should stay narrow, and a mistake here has a real person's real balances behind it. Preview and Development stay on Sandbox by env scoping; `PLAID_REDIRECT_URI` is All Environments, so an OAuth link started from a preview deploy returns to the production origin and loses its queue.
- **Dark mode on the live app themes via the design system; verify per-page rather than assume** - the live shell picks up `.dark .jnpr`, so it follows the theme end to end. Marketing and auth pages sit outside the `.jnpr` surface and stay light by design. If an individual page looks off, verify and patch that page's tokens; it is not a known systemic gap.
- **Plaid service-role key is a high-value secret** - `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely and is what reads the `plaid_items` token store. It lives only in Vercel env; it must never reach the client bundle or a `VITE_`-prefixed var.
- **"Accounts I use" (onboarding) is still localStorage-only** - Plaid linked-institution names come from the server, but the onboarding-captured list they are merged with is client-side, so that half does not sync across devices.
- **Apps Script webhook secret is committed** - the growth pipeline's shared secret (`jnpr_whk_...`) is hard-coded in `juniper-sheet-webhook.gs`. Those files sit outside the git repo, but the secret is plaintext; rotate before any wider sharing.
- **Growth pipeline is out-of-repo** - the `.gs` files live in the parent directory and are not version-controlled with the app, so their state can drift silently.
- **Em-dash leakage** - Claude keeps emitting the character despite strict prompts; mitigated by a client-side strip in `displayContent()`, but any new surface that bypasses that helper will leak.
- **GRANT footgun for new tables** - SQL-migration-created tables do not auto-grant Data API access. New tables silently return 401 without `GRANT ... TO authenticated`. Baked into migrations 0002+ but easy to forget.
- **Env-var newline footgun** - past `Invalid header value` outages came from copy-pasted env vars with embedded newlines. `api/_env.ts` sanitizes on read; any new server-side env reader should use it.

## Notable debug lessons

Subtle enough to repeat, so worth keeping a section:

- **A total computed from a different source than the list it sits above will drift, and it can drift all the way to zero.** The shared Overview drew each side's accounts from per-account scopes and then computed the headline figure from a coarse pref and a full-account sum, so the two could never contradict each other loudly enough to be noticed: the list was right, the number was 0, and sharing an account changed the first and not the second. A figure that summarises a list has to be accumulated in the same pass over the same rows with the same skip rule, not derived independently and trusted to agree.
- **A fixture that cannot exhibit the bug will certify the bug.** #188's layout harness used short merchant names, so no row wrapped, so nothing overflowed, so a list that could not overflow passed a test about overflow and shipped a trapped scroll wheel (#189). When measuring a layout, build the fixture from the content that stresses it, the two-line merchant name and the thirteen-account column, not from tidy sample data.
- **Two timestamps on a row can both be wrong for one question.** "How old are these balances" looked answerable from `plaid_items` twice over and was not: `last_synced_at` is written by transactions-sync as well, and the one item that needed the answer syncs transactions perfectly while every balance call times out, so it read as freshly synced forever; `updated_at` is trigger-maintained and moves on any write, including the cursor. A timestamp is only trustworthy for the fact it is written beside. `balances_refreshed_at` is written in exactly one place, next to the snapshot it dates.
- **An early-return flag has to be read from the side you control.** Plaid's Link still hands back a public token in update mode, and exchanging it mints the duplicate item that update mode exists to prevent. The safe read is the repair flag the app put on its own queue, not the metadata coming back from the SDK.
- **A timeout is not a refusal, and treating them alike loses a whole strategy.** `/accounts/balance/get` timing out means the bank is slow; a dead item or a permissions error means the data genuinely is not available. Only the first has a good fallback (`/accounts/get`, Plaid's own cached balance, no round trip to the bank). Collapsing the two would either paper over real errors with stale figures or throw away the one bank that needed the fallback.
- **An empty-state branch can sit above the feature that fills it.** The Plans page returned "No plans yet" on `views.length === 0` before reaching the grid, so the goal cards added in #184 were unreachable for exactly the member they were built for, and the Overview half shipping fine made it look like a partial deploy rather than a bug. When adding a case to a list, check what returns before the list is rendered.
- **A shared frame that replaces children makes its own links unreachable.** `SharedPage` swapped in the blank canvas on every shared route while the space was empty, so following the canvas's "A bill" tile landed on Bills and rendered the canvas again, and the first bill could never be added, since the tab only appears once a bill exists. A frame should own one screen, not override every screen beneath it.
- **A permissive default is a decision nobody made, and it outlives the code that set it.** `share_balances` was `DEFAULT TRUE` in a migration and `true` again in a code default, and a third fallback in `scopeFor` agreed with both, so three independent layers all said "share it" and none of them had ever asked. The product copy said the opposite, in writing, in the same modal that created the partnership. When a default decides who sees somebody else's bank balances, the safe direction is the revoking one, and closing existing rows matters as much as changing the column: the flip alone would have protected only future partnerships.
- **A batch is a barrier, and a barrier is not concurrency.** Slicing items into rounds of six and awaiting each round means round two cannot start until the slowest bank in round one answers, so one twenty-second institution parks five idle workers and leaves six items untouched. The fix that looks done is only half done until the rounds become a pool: workers pulling from one cursor with nothing to wait on. Same shape as any "chunk and `Promise.all`" loop over a slow remote.
- **Budgeting the slow call is not budgeting the work.** `networth-snapshot` stopped starting new items at 18s and was still killed at 25, because the per-item work is a Plaid call plus two Supabase writes and only the Plaid call was inside the budget. A deadline has to reserve for the tail after the thing you were timing.
- **An incremental cursor means a feature added today never reaches yesterday's rows.** Merchant art shipped as a column filled by `/transactions/sync`, which by design never revisits a row, so a member whose history had already synced saw no art at all and would keep seeing none until each merchant charged them again. The general move is a lookup table keyed by the thing the data is a fact about (the merchant), not the row, so one write repairs the whole history without replaying the sync.
- **Returning early is a correctness requirement when the same function also deletes.** A recurring sync that reconciles against Plaid's answer deletes what Plaid no longer returns. Under a permissions error Plaid returns nothing, which is indistinguishable from "nothing recurring any more" if you keep going. The refusal has to short-circuit before the upsert and before the delete, not just be logged more quietly.
- **A card that renders art is not a card that asked for art.** The Overview transactions card showed monograms for weeks after merchant art shipped, and the cause was two layers up: `/api/finances` selected no `logo_url` and did no cache lookup, and the row component was the older `BrandTile`. When one surface disagrees with another about the same data, check what each one actually requested before debugging the renderer.

- **A fixed averaging window over a variable history inflates every ratio built on it.** `_finance-snapshot.ts` divided by a constant 90 days while a member had three weeks of transactions. That did not make the numbers noisy, it made them wrong in a consistent and flattering direction: emergency fund read 3x the months it actually covers, investing pace 3x the pace, debt load a third of the burden. The only figure that survived was savings rate, and only by luck, because it is a ratio of two numbers that were both a third too small. Any "per month" figure must divide by the history that exists, not the window that was requested.
- **A neutral placeholder inside a weighted score is not neutral.** `creditFactor` returned a flat 70 when there was no credit data. That was 10.5 points of a score presented to the member as their own, and because a 70 leaves the most headroom, it won the "biggest lever" ranking, so the app's single loudest instruction was to improve the one thing it had no data about. The fix is to drop an unmeasured component and renormalize the remaining weights, never to fill it in with a plausible number.
- **Reading the sign of a transaction is not reading what happened to the money.** `/api/finances` treated every outflow as spending and every inflow as income, so a transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent. The card payment was the worst case and the one nobody spots by eyeballing a total: the purchases it pays for already counted when they happened, so the member was billed twice in the same month for the same coffee. Only the category can tell a card payment from a car payment, and Plaid's *detailed* `personal_finance_category` is the level that carries it (the primary cannot). The blast radius reached past the dashboard, because spending and income feed the Score's savings rate and emergency-fund factor. Anything that classifies money by sign alone is wrong in the same way.
- **One AND-gate over two independent sources withholds both, and a loop that returns on first failure turns one bad item into an outage.** `api/finances.ts` required items AND transactions before returning anything, so real, already-stored balances were queued behind a feed that arrives minutes later and sometimes never. In the same PR: `networth-snapshot.ts` returned 502 the instant one item's balance call failed, and the snapshot rewrite sat inside that loop, so one broken connection meant nothing refreshed at all, while the caller discarded the response body and showed no error. Gate per section, isolate per item, and report what failed.
- **Deleting demo data makes degenerate shapes reachable for the first time.** Removing the mock layer meant `NetWorthChart` could finally receive a one-point series, a dead-flat series, and a negative series; it divided by `series.length - 1` and scaled bounds by 0.985/1.01, so all three produced NaN paths or inverted bounds. The same removal exposed a delta chip hardcoded to "up", safe only while the number came from a demo household that always rose. Seed data is not just wrong content, it is a shape filter hiding the empty and edge cases.
- **Check the account before the config** - a Plaid entitlement that looks inexplicably stuck is more likely the wrong account than a broken setting. Five months of "Production under review" were a different client ID's dashboard. Same shape applies to any per-account SaaS console.
- **Probe env changes without signing in** - `curl -X POST .../api/plaid/link-token -d '{}'` returns 401 when creds are present and 503 when `plaidConfigured()` is false, which distinguishes "Vercel has not picked up the env yet" from "auth is rejecting me" in one call. Plaid's real reason lands in the server log (`[plaid] link/token/create failed`), and the Vercel runtime-log query needs a short `since` window or it times out.
- **Env vars with embedded newlines** — `SUPABASE_ANON_KEY` had a `\n` at position 208 from a copy-paste. Node fetch headers reject CR/LF. `api/_env.ts` strips non-printable chars from all server-side env reads.
- **ES256 vs HS256** — Newer Supabase projects use asymmetric JWT signing keys (ES256). Legacy "JWT Secret" doesn't sign user tokens anymore. `api/_supabase-jwt.ts` checks `header.alg` and routes to JWKS (ES256) or HMAC (HS256) accordingly.
- **GRANT for raw-SQL tables** — Tables created via SQL migration don't auto-grant Data API access. Every new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated;` or every request returns silent 401.
- **Unescaped backticks in template literals** — `BASE` prompt had backticked angle brackets inside a backtick-delimited string. JS parser closed the template early and tried to interpret the rest as tagged template expressions ("X is not a function" at module load). Don't use backticks in prose inside backtick-delimited strings.
- **PostgREST OR filter quirks** — `or=(user_id.eq.X,partner_user_id.eq.X)` returned `[]` even when matching rows existed. Switched to two parallel queries + client-side merge.
- **Double-read of fetch response body** — `/api/plans` GET error path was reading `.text()` after `.json()`; fixed by buffering once and reusing.
