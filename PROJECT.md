# Juniper
*AI copilot for couples navigating major financial life transitions.*

*Last updated: 2026-08-26 by Claude Code (Plaid Production resolution)*

---

## TL;DR

Juniper helps engaged and newly married couples model the financial tradeoffs behind big decisions (buying a home, combining finances, paying down debt, planning for a baby, prenups) and align on them before commitments are made. All five domains run end-to-end in production at `juniper-api-server.vercel.app`; the phase is post-MVP GTM iteration. **Plaid Production access is resolved as of 2026-08-25.** The five-month "application under review" stall was not a Plaid backlog: Finley had been reading the dashboard of the wrong Plaid account the whole time. The correct account (`PLAID_CLIENT_ID=6a4ec8ec24799a000d0936d1`) is approved for Production at the "approved to test with real data" tier, with **Transactions (1/200), Balance (1/200), and Investments (0/200)** enabled; the `/200` is that tier's Item cap, and full production volume still needs the complete production agreement. Vercel env is now split by environment so preview and local can never touch a real bank: `PLAID_ENV=production` plus the production secret on Production, `sandbox` plus the sandbox secret on Preview and Development, and local `.env` stays Sandbox. OAuth redirect URIs are registered on the new account for `juniperplan.com`, `www.juniperplan.com`, and `juniper-api-server.vercel.app`, which unblocks the large banks (Chase, BofA, Wells, Capital One) that route through OAuth. What remains is compliance, not wiring: a financial-data TOS and privacy policy plus a security review of the data surfaces before broad public linking, and affiliate URLs are still `example.com` placeholders pending licensing. Dark mode shipped earlier and is live (PR #117).

## What it is

**The problem:** Couples make huge financial decisions (home, debt, kids, prenups) without forward-looking modeling, and money conversations between partners are emotionally loaded and often avoided.
**The solution:** A neutral AI copilot that runs each partner through the same scripted dialogue, synthesizes a shared plan, and shows side-by-side where they agree and where they don't.
**The user:** Engaged or newly married couples, late 20s to early 40s.
**The value:** A structured, low-emotion way to surface tradeoffs and align before the irrevocable decision gets made.

- **2026-08-25 - Verify which Plaid account the dashboard is showing before debugging any entitlement** - Five months of "Production under review" were spent debugging config against the wrong Plaid account. Application status, product entitlements, and allowed redirect URIs are per-account and per-client-ID, and none of it transfers when you switch accounts. The alternative (one shared production secret) would let any preview deploy or local branch pull real bank data and burn Items against the 200 cap. Vercel allows duplicate names only when scopes do not overlap, so shrink the existing row before adding the second.
- **2026-08-07 — Dark-mode toggle belongs in the live settings modal, not the retired shell (corrects #116)** — PR #116 wired the toggle into `ProfileSettings` + `app-shell.tsx`, but the running app is the newer JuniperApp shell (`pages/juniper-app.tsx` + `components/juniper/*`), so the control shipped into unreachable dead code. Fix: add the toggle to the live `components/juniper/settings-modal.tsx` (wired to the existing `useTheme()`, `.jnpr`-styled) and revert #116's edits to the retired files so there's a single source of truth and no divergent second settings modal. The theme engine (`theme.tsx`, `index.html` pre-paint, `App.tsx` provider, `.dark .jnpr` palette in `juniper.css`) was already live and correct — only the *control's location* was wrong. This also supersedes the 2026-08-07 "dark mode ships core surfaces only" decision **for the live app**: the JuniperApp shell themes through the `.dark .jnpr` design system, so it already follows dark mode end-to-end; the partial-scope caveat described the retired shadcn shell (`.dark {}` in `index.css`), not the live surfaces.
- **2026-08-07 — Theme state on `<html>` class + CSS variables, palette in `index.css`** — `theme.tsx` only decides which palette is active (toggles the `dark` class); the actual colors live as `:root` / `.dark` CSS-variable sets in `index.css`, so surfaces reference `hsl(var(--token))` and flip for free. Choice persists to `localStorage["juniper_theme"]`, defaults to OS `prefers-color-scheme` on first visit, and a pre-paint inline script in `index.html` applies it before React mounts to avoid a flash-of-wrong-theme. The scaffolded `.dark {}` block previously held `red` placeholders for every token, so dark mode had never actually worked before this fill-in.
- **2026-08-04 — Account discovery is three tiers, not one "magic" flow (Stage 13)** — The Credit Karma "enter your info and everything appears" moment is a *credit-bureau pull*, not account aggregation: it only ever populates credit accounts (cards/loans), never bank balances, investments, or transactions, which aren't in a credit report. Juniper is Plaid-based (aggregation), so the honest analog is Plaid **Layer**: phone number in, and Plaid surfaces the accounts the person has *already connected across the Plaid network*, one-tap, no per-institution login. But Layer only knows network-known accounts, so it can't stand alone. The connect experience is therefore three tiers, most-magic-first and each degrading into the next: **(1) Layer** (phone-first instant discovery, gated on Plaid Production + a Layer template), **(2) a searchable, sorted, multi-select institution gallery** with Select all + a sequential Plaid Link queue (works today on Sandbox), and **(3) manual add** for institutions Plaid can't link (small/regional banks, many 401(k)s) so net worth can still be complete. Tiers 2 + 3 are permanent fixtures, not stopgaps.
- **2026-08-04 — "Select all" is real only at tier 1; tier 2 is a sequential queue** — Plaid Link authenticates one institution per session, so a gallery "select all → connect" can't batch-auth; it opens each selected institution's login in turn (`use-link-queue.ts`, ref-driven so callbacks never read a stale queue position, skip-on-exit, "Connecting 2 of 4…"). True one-tap-for-many only exists at tier 1 (Layer), where the accounts are pre-permissioned in the network. The gallery still gives the *selection* UX the user wants; the linking is honest about per-bank auth.
- **2026-08-04 — Layer shipped as an inert, flag-gated seam** — `api/plaid/layer-session.ts` + `createLayerSession()` + `layerEnabled()` (`VITE_PLAID_LAYER`) + a gated `LayerDiscovery` phone-entry component are wired into onboarding and Connections but return 503 / stay unmounted until `PLAID_LAYER_TEMPLATE_ID` is set and the flag flipped, the same "build the seam now, activate at the gate" pattern as the rest of the data engine. Layer's multi-item return + exchange can only be exercised on Plaid Production, so the scaffold reuses the standard public-token exchange and is explicitly marked to re-verify end-to-end at go-live.
- **2026-08-04 — Manual accounts in their own client-readable table** — `manual_accounts` (migration `0014`) follows the `plans`/`transactions` pattern (owner RLS + Data API grants), the deliberate opposite of the server-only `plaid_items` token store: this is the user's own hand-entered data, no secrets. The API writes via the service-role key and scopes every write by `user_id` itself. Balance magnitude is stored positive; sign comes from `kind` (asset/liability), which the category implies.

- **2026-07-08 — Plaid access token in a server-only table, never client-readable** — `plaid_items` (migration 0007) is the deliberate inverse of every other table: `REVOKE ALL` from anon/authenticated, RLS with a restrictive `USING (false)` policy, `GRANT ALL` to `service_role` only. Edge functions reach it with the Supabase service-role key; the browser only ever receives sanitized account snapshots (no tokens, no account/routing numbers). A leaked user JWT reading via PostgREST gets zero rows.
- **2026-07-08 — Call Plaid over `fetch`, no SDK** — The Plaid Node SDK isn't edge-safe, so the four `api/plaid/*` endpoints call Plaid's REST API directly via `fetch` through a thin `api/_plaid.ts` wrapper. Keeps the functions on the Edge runtime like the rest of `api/`.
- **2026-07-08 — Ship Plaid on Sandbox in production, gate real data on Plaid review** — Link + display works end-to-end in prod against Plaid Sandbox (verified with Tartan Bank). Going live on real bank data requires Plaid Production access (application review + beneficial owners + billing) — a compliance gate parallel to the affiliate-licensing one. `PLAID_PRODUCTS` and the stored snapshot are shaped to grow into transactions/liabilities/investments and auto-filled plan inputs; those data tiers are deferred until the gate clears.
- **2026-07-08 — WAU = distinct `user_id` with an `engaged_session` in trailing 7 days** — Rather than raw page views, engagement is a single canonical `engaged_session` GA4 event fired once per browser session (module-level guard) at genuinely meaningful moments, with a GA4 `user_id` set for signed-in users. Makes WAU a clean distinct-user count. Reporting adds a WAU column to `juniper-growth-ga4-pull.gs` (out-of-repo).
- **2026-07-08 — Marketplace listings carry a `source` provenance field** — `partners.ts` listings are tagged `curated | scraped | self-listed` so a bootstrapped grid (scraped from public listings, DoorDash-style) can coexist with real self-listed merchants later. Still code-config, not a table; all URLs remain `example.com` until affiliate licensing clears.
- **2026-07-08 — Portfolio summary is a pure client-side rollup** — The dashboard summary for 2+ plans aggregates already-fetched plan data (reusing `buildProjectionView`) with no backend, migration, or new API call. Cheapest path to a cross-plan view; revisit if it needs server-side aggregation.

- **Dark mode on the live app themes via the design system; verify per-page rather than assume** — the live JuniperApp shell (`components/juniper/*`) picks up dark mode through `.dark .jnpr` in `src/styles/juniper.css`, so the shell follows the theme end-to-end; the earlier "only core surfaces themed" caveat applied to the *retired* shadcn shell (`.dark {}` in `index.css`), not the live app, and no longer describes it. The marketing/landing and auth pages sit outside the `.jnpr` app surface and stay light by design. If any individual live page looks off in dark mode, verify and patch that page's tokens — it's not a known systemic gap.
- **Partner URLs, logos, and rates are demo placeholders** — every affiliate `url` is `example.com`, logos come from a favicon service, and projection rates are fixed constants. Regulated categories (mortgage, insurance, credit cards, legal) likely need specific disclosures/licensing. Do not launch monetized surfaces on these; they are plumbing/UX only.
- **Anthropic cost is uncapped** — no spending limit configured. Per-plan spend dropped this session (structured steps no longer call the LLM; synthesis is ~1 call per plan), but a runaway prompt loop or abuse could still spike.
- **Plaid now talks to real banks in production** - as of 2026-08-25 Production runs the production secret with `PLAID_ENV=production`, so linked accounts are real people's real balances, held as an `access_token` in the server-only `plaid_items` table. Three live constraints: the tier caps Items at 200 per product, the Stage 6 compliance pair (financial-data TOS + privacy policy, security review) is not done yet so linking should stay narrow, and no real bank has actually been linked end-to-end since the switch, so the production path is approved but unproven. - **Plaid service-role key is a high-value secret** — `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely and is what reads the `plaid_items` token store. It lives only in Vercel env (Production + Preview); it must never reach the client bundle or a `VITE_`-prefixed var.
- **"Accounts I use" (onboarding) is still localStorage-only** — Plaid linked-institution names now come from the server, but the onboarding-captured list they're merged with is still client-side; that half doesn't sync across devices.
- **Apps Script webhook secret is committed** — the growth pipeline's shared secret (`jnpr_whk_...`) is hard-coded in `juniper-sheet-webhook.gs`. Those files sit outside the git repo, but the secret is plaintext; rotate before any wider sharing.

- **Em-dash leakage** — Claude keeps emitting `—` despite strict prompts; mitigated by client-side strip in `displayContent()`, but any new surface that bypasses that helper will leak.

- **Env-var newline footgun** — Past `Invalid header value` outages came from copy-pasted env vars with embedded `\n`. `api/_env.ts` sanitizes on read; any new server-side env reader should use it.

## Notable debug lessons

Subtle enough to repeat, so worth keeping a section:

- **Check the account before the config** - a Plaid entitlement that looks inexplicably stuck is more likely the wrong account than a broken setting. Five months of "Production under review" were a different client ID's dashboard. Same shape applies to any per-account SaaS console.
- **Probe env changes without signing in** - `curl -X POST .../api/plaid/link-token -d '{}'` returns 401 when creds are present and 503 when `plaidConfigured()` is false, which distinguishes "Vercel has not picked up the env yet" from "auth is rejecting me" in one call. Plaid's real reason lands in the server log (`[plaid] link/token/create failed`), and the Vercel runtime-log query needs a short `since` window or it times out.
- **Env vars with embedded newlines** — `SUPABASE_ANON_KEY` had a `\n` at position 208 from a copy-paste. Node fetch headers reject CR/LF. `api/_env.ts` strips non-printable chars from all server-side env reads.
- **ES256 vs HS256** — Newer Supabase projects use asymmetric JWT signing keys (ES256). Legacy "JWT Secret" doesn't sign user tokens anymore. `api/_supabase-jwt.ts` checks `header.alg` and routes to JWKS (ES256) or HMAC (HS256) accordingly.
- **GRANT for raw-SQL tables** — Tables created via SQL migration don't auto-grant Data API access. Every new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated;` or every request returns silent 401.
- **Unescaped backticks in template literals** — `BASE` prompt had backticked angle brackets inside a backtick-delimited string. JS parser closed the template early and tried to interpret the rest as tagged template expressions ("X is not a function" at module load). Don't use backticks in prose inside backtick-delimited strings.
- **PostgREST OR filter quirks** — `or=(user_id.eq.X,partner_user_id.eq.X)` returned `[]` even when matching rows existed. Switched to two parallel queries + client-side merge.
- **Double-read of fetch response body** — `/api/plans` GET error path was reading `.text()` after `.json()`; fixed by buffering once and reusing.

## Env vars (Vercel + frontend)

- `PLAID_PRODUCTS` (backend, optional, default `transactions` since PR #122; was `auth`, which Juniper never needed), `PLAID_COUNTRY_CODES` (backend, optional, default `US`), `PLAID_REDIRECT_URI` (backend, All Environments) - only for OAuth banks, and the value must be registered in the Plaid dashboard of the *same* account as `PLAID_CLIENT_ID`.
