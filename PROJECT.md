## What it is

**The problem:** Money is spread across banks, cards, brokerages and loans, and there is no single honest view of where a person stands or what a decision would cost them. The tools that try either invent numbers to fill the gaps or stop at a budget.
**The solution:** A planning app that reads the member's own linked accounts and turns them into a net-worth trend, spending that means consumption rather than every outflow, a 0 to 100 Juniper Score built only from what it can actually measure, and plans funded from real balances. A partner can be invited as an optional layer on top; nothing crosses to them until it is explicitly shared.
**The user:** Individuals and families, late 20s to early 40s. Solo is the default experience, not a fallback.
**The value:** One place that tells a member the truth about their own money, with a next step attached to each number.

*This supersedes the original couples-first framing. The repositioning is Stage 0 in ROADMAP.md ("audience: individual-first, partner as a layer"), and as of #171 to #177 it is built: the personal app is complete on its own, and the shared space is a second workspace you switch into.*

**A reconstruction can be redone when its inputs change** (#256, and the production run recorded in #257). `networth-backfill` fires on every sync and writes with `resolution=ignore-duplicates`, which was two rules in one: never overwrite an OBSERVATION with a guess, which is always right, and never re-derive a guess, which is right by default, because a reconstruction walks back from TODAY's balances and therefore moves as the market moves, so rewriting it on every sync would make a member's May net worth wobble daily. The second rule is wrong in exactly one case, when the INPUTS change, which is what the Schwab relink did. `POST ?rebuild=1` replaces only the days the endpoint reconstructed itself. The decision is `replaceableDays` in `api/_networth-walk.ts`, kept pure because it drives a DELETE on the one table in the app that cannot be recomputed: `net_worth_snapshots` is keyed by (user, day), so a lost observation is lost for good, while a reconstruction can always be rebuilt. `scripts/src/check-networth-rebuild.ts` asserts over **4096 combinations** that a recorded day is never deletable and that a day the walk did not produce is never touched, so a failed walk cannot empty a history. The delete sends `estimated=eq.true` alongside the day list, so the database refuses an observation even if the list were ever wrong, and the endpoint warns when rows-deleted and days-planned disagree. It is triggered from **Settings, Developer, "Rebuild net-worth history"**, which reports what it did rather than saying "Done"; `syncFinances()` deliberately does not pass the flag.

**The rebuild ran once, on 2026-09-02, and Schwab answered.** Pressed from Settings: **92 reconstructed days replaced, 6 recorded days left alone, investments adjusted for contributions on 1 connection**. The outcome was checked in the database rather than read off the message: the table now holds **92 reconstructions and 8 observations** (the daily job has since written 2 September), every recorded day survived the delete, and the trend is no longer flat, with reconstructed June spanning about $10,900 and July about $10,600 against a series running from roughly **$81,600 in late May to $100,200 now**, where before the rebuild about 73% of net worth was held constant across the whole reconstruction. **Still not exact, and it cannot be:** the invested portion counts money added, not market movement, because Plaid reports today's prices only. Income and Transfers are offered alongside spending, because "this was a credit card payment, not shopping" is the correction most worth making. The cost, stated because it is real, is that the picker stops being a single-purpose control. The create list offers every group with the kind labelled on the row, since `api/categories.ts` refuses to move an existing leaf across kinds and creating one inside Transfers is therefore the supported route to a category that is not spending. Delete is offered only on categories the member created; a built-in cannot be deleted because the next sync would write its label again, so **Hide** is what a built-in gets instead, with "Show N hidden" at the foot of the list and Unhide on each. The count of transactions per category is deliberately absent from the list and appears only in the refusal that needs it ("3 transactions still use this category. Move them first."). Duplicate names are refused inline before any request, with the server still the authority, and Escape closes an open form before it closes the panel

A member choosing their own icon gets the full list, 1,898 emoji, and is not held to that ceiling, because it is their own screen. The dataset is generated from Unicode and CLDR and imported dynamically by the picker and nothing else, so it lands in its own 32KB gzipped chunk and the main bundle grew about 4KB. **The list is filtered by what the machine can actually render**, measured against the missing-glyph width rather than trusted to a version table, 17ms for the whole list once, erring toward dropping a real emoji rather than showing a box. A created category gets a label tag rather than borrowing its group's icon, and a rename keeps the icon

Healthy reads "Updated 4 minutes ago", a finished connection reads "Needs reconnecting" with the date its balances stopped, and a connection permanently on Plaid's cached balances says so. Every fact behind that was already recorded and never asked for: `last_synced_at` and `last_error_code` since migration 0017, `balances_refreshed_at` since 0022, `balances_from_cache` since 0023. `accounts.ts` requests the health columns and retries the same select without them if it fails, because PostgREST rejects a whole select on one unknown column, so a deploy that runs ahead of a migration degrades to the old response with `health_unavailable` rather than 500ing. **Reconnect uses Plaid update mode:** `link-token.ts` reads the item's `access_token` server-side and sends it *instead of* `products` (Plaid rejects `products` in update mode), so Link repairs the existing item rather than minting a second one beside the dead one. The trap is the return trip, since Link still hands back a public token and exchanging it creates exactly that duplicate, so `use-link-queue.ts` reads the repair flag off the queue rather than Plaid's metadata and returns before the exchange. **The update-mode path has never executed:** it needs a genuinely dead item and all seven connections are healthy

This fills `merchant_logos` from `/transactions/get` over a 180-day window, leaving sync state alone, and `api/transactions.ts` resolves a row as `t.logo_url ?? logoOf.get(t.merchant_name)`, so one merchant-level upsert covers a whole history. It asks the database which merchants are missing first and returns without calling Plaid when none are, which is what makes it safe on every refresh and from the cron
- **One refusing bank costs its own balance, not the day, and not forever** *(PRs #180, #183, #187, `api/plaid/networth-snapshot.ts`)*: an item that fails now contributes its last known balances from the stored `plaid_items.accounts` snapshot and the row is written with `estimated = true`, rather than the whole day's trend point being dropped. Skipping survives only for an item that has never refreshed at all, where there is no last known balance to carry. The run also reserves `WRITE_RESERVE_MS` (4s) of its 18s deadline for the tail after the Plaid call, since `refreshItem` is a Plaid call plus two Supabase writes and only the call had been inside the budget, which is why the function was still being killed at 25s. **#183 put a ceiling on the carry at seven days** (`CARRY_MAX_DAYS`), because an item that never comes back would otherwise fold a frozen number into every future total, presented as today's, and the only signal would be a dashed point indistinguishable from a legitimate reconstruction; past the cutoff the item stops contributing and the day is skipped honestly, which is what the original rule protected. An item that never refreshed and one whose balances went stale are counted apart in the log, and `carry_expired` rides on the response so a trend that stops receiving points explains itself outside the logs. **#187 then made the slow bank answer at all:** on a timeout only, never on a dead item or a permissions error, the endpoint falls back to `/accounts/get`, which returns the balance Plaid already holds with no round trip to the bank, in about a second. The fallback is budgeted from the run's remaining time rather than the budget of the call that just timed out. `balances_refreshed_at` (0022) is written here and nowhere else, beside the snapshot it dates, and `balances_from_cache` (0023) records which of the two paths wrote it
- **Plaid calls have deadlines, and the pool has no barrier** *(PRs #152, #162, `api/_pool.ts`)*: a member with twelve institutions was getting a 504 on `/api/plaid/networth-snapshot`, because the loop was serial and `/accounts/balance/get` goes to the bank for a live balance, so its latency is the bank's. #152 batched six at a time; #162 finished the job, because a batch is a barrier and one twenty-second bank parked five idle workers. `mapPool` is six workers pulling from one cursor, pure and importing nothing. Every `plaidFetch` now carries a timeout (15s default, tighter when a caller is walking a whole connection list), a timeout returns `JUNIPER_REQUEST_TIMEOUT` which is deliberately not a dead-item code, and a transport failure comes back as a result rather than a throw, because one rejection inside `Promise.all` abandons the others mid-flight
- **Recurring detection is entitled, and the sync still degrades rather than shouting** *(PRs #155, #165, #221, `api/plaid/recurring-sync.ts`, `api/plaid/link-token.ts`)*: `recurring_transactions` is a separate Plaid add-on, not entitled under Transactions, and production settled that on 2026-08-28 with every item returning 400 `INVALID_PRODUCT`. **Plaid granted the add on on 2026-08-31**, and #221 then added it to `additional_consented_products`, which broke `/link/token/create` for every member for a day until #234 removed it: that field takes the `products` enum and an add on is not in it, so recurring detection needs nothing at link time. See `docs/RECURRING_DETECTION.md` section 2 before touching a consent list. The refusal handling below is kept, not removed, because it is what makes an entitlement change safe in either direction. The endpoint used to make that as loud as possible, six error lines and a 502 every six hours on a background leg whose body the caller drops. The first item to hit an entitlement refusal now sets a flag, every queued item skips its call, one warning is written, and the endpoint answers 200 with `available: false`. Critically it returns **before** the upsert and before the delete: falling through with zero rows would read as "Plaid no longer detects any of your streams" and wipe the member's cached list on the strength of a permissions error. Per-item failures are untouched
- **Persisted per-item sync state** *(PR #156, migration 0017)*: `needs_relink` used to be computed inside a sync the member had just triggered and then thrown away, so a page load could not tell a connection whose login had expired from one that was simply quiet. `plaid_items` now carries `last_synced_at`, `last_error_code` and `last_error_at`, written by all three sync endpoints through one shared helper (`api/_item-sync-state.ts`). Only dead-item codes are recorded: a transient failure resolves on the next run, and surfacing those would train people to ignore the one message that matters

Helpers `api/_plaid.ts` (Plaid fetch wrapper) and `api/_supabase-admin.ts` (service-role client). The Plaid `access_token` never leaves the server
- **Spending means consumption, and every category means something** *(PR #136, `api/_categorize.ts`)*: `/api/finances` used to read only the sign of a transaction amount, so every outflow was spending and every inflow was income. A transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent, and the card payment was the worst of it, because the purchases behind it already counted when they happened, so the member was billed twice in the same month. `_categorize.ts` is now the single taxonomy table: **11 groups** (9 spend, 1 income, 1 transfer) over **46 leaf categories**, driven by Plaid's *detailed* `personal_finance_category` with the primary as a floor. Since #206 to #213 that table is the built-in layer a member's own categories and groups sit on top of, resolved per request by `taxonomyFor()`, and the module itself is documented as pure and I/O-free so the sync, the read endpoints and the score snapshot can all share it. Each group carries a `kind`, and three rules follow from it: `transfer` is ignored entirely, `income` is netted from its own categories, and `spend` is summed **signed**, so a refund reduces the category it came back to instead of masquerading as income. Groups are derived at read time and never stored, and `spent` is *defined as* the sum of the breakdown, so the card header, the donut center, and the cashflow strip cannot disagree. The same three rules run in `api/_finance-snapshot.ts`, which is why this reaches past the dashboard: those two numbers feed the Juniper Score's savings rate and emergency-fund factor. - **Net-worth backfill** *(PR #147)*: `api/plaid/networth-backfill.ts` walks backward from today's balances through the transactions that moved them (`cash(day-1) = cash(day) + that day's depository total`, `owed(day-1) = owed(day) - that day's credit total`, `invest(day-1) = invest(day) - external inflow`). Investments cannot be reconstructed exactly (market movement is not a transaction and Plaid has no historical price feed), so the invested balance is today's holdings minus net contributions since, read from `/investments/transactions/get`. ## Risks & known issues

- **The arranging UI has only ever been driven in a harness with stubbed endpoints.** The board, edit mode, the shelf, both new widgets, the keyboard path, the drag, the persisted value and the no-transaction-feed path were all exercised against the real components, which is stronger than reading them and weaker than a real session: nothing has moved a card on a real phone, and no member's layout has been read back on a second device. `arranged` is 0 on production.
- **A layout is written by the client into a column whose CHECK does not police the widget ids**, deliberately, since the ids are the app's registry. The guards are the shape check in 0049 and `asDashboardLayout` on the way in, which drops any id the build does not know. A stale build reading a newer layout therefore drops the ids it has never heard of and keeps the rest, which is the intended degradation, but it does mean the ONLY thing standing between a malformed layout and the renderer is a client-side narrow.
- **Net worth lost its wider column and it is not coming back while ordering is free.** The 1.5fr/1fr hero could not survive a member moving one card at a time. Recorded as a known regression in the reading of the page rather than as a neutral change.
- **The card art is the issuers' own marketing renders, rehosted without a license.** Deliberate, stated in `0037`'s header, with a one-line revert and three legitimate routes written beside it, and the trim work (margins, and the issuers' placeholder cardholder names) was done so a stranger's name never appears on a member's card. It is still 32 issuer assets served from Juniper's origin, so it is a legal exposure that grows with the member count rather than a technical one, and it closes on an affiliate brand pack or a licensed vendor.
- **Ten catalog products carry rates nobody has re-checked.** `verified` is FALSE on everything `0032` seeded, and the page says so, which is the honest version and not a fix: those ten are the common US cards most likely to be a real member's card. The eleven Chase products in `0040` and the premium three in `0042` ship `verified = TRUE` because their rates were read from the issuer's own rewards-program text.
- **The catalog understates every card whose headline rate is portal- or merchant-scoped**, because the earn taxonomy has no way to say "through Chase Travel" or "at Amazon". Prime Visa, Amazon Visa, DoorDash, Instacart, both Sapphire Reserves, Ink Business Premier, the Amex Platinum and the Venture X are all affected, and the Platinum reads as a 1x card. Understating is the safe direction for a card being recommended and the unsafe one for a card the member holds, which is why those two cases are separated in the catalog; a member holding one of these will still see a guide that undersells it.
- **A member-typed credit limit is one widened `select` away from reaching the Juniper Score.** The isolation is structural (a separate fetch, one importer, and `check-manual-limit-isolation` asserting fourteen facts about it) precisely because the failure is silent and self-serving: a member could raise their own score by typing a generous number. The check is the guard; anybody adding a column to the shared manual-accounts select needs to see it fail.
- **Five manual credit accounts count as card debt in net worth, and any duplicate of a Plaid-linked card double-counts.** They predate the Credit page showing them, so nobody has reconciled the set. A duplicate would inflate both net worth's debt side and the utilization denominator.
- **The rebuild's DELETE is the only destructive write in the app.** Two filters stand between a bad day list and a lost observation: `estimated=eq.true` sent alongside the list, and `replaceableDays` never proposing a day the walk did not produce. Both are asserted by a pure check over 4096 combinations, and the worst realistic failure is deleting reconstructions that the same run immediately rewrites. It has run once in production, successfully.
- **The invite preview depends on six meta tags existing in `index.html` by name.** A rewrite of that block would make each replace a no-op and the preview would quietly revert to the marketing card, which is why the function checks every swap rather than trusting it. What is not covered: nothing watches the live preview, so a regression would surface as somebody's invite looking wrong.
- **A one-string change to the consent list took bank linking down for a day, and what is left of that risk is the shape of it rather than the string.** #221 added `recurring_transactions` to `additional_consented_products`; Plaid refused every `/link/token/create` from that moment until #234 removed it on 2026-09-01. Linking is the highest-blast-radius call in the app: it fails for every member at once, including anybody part way through onboarding, and there is no partial version of the failure. Two things kept it invisible for a day rather than minutes, and only one is fixed. The client collapsed every failure to null and rendered "Account linking isn't enabled yet", which is now gated on a 503 (#234). **Nothing yet watches that endpoint**, so the next time it breaks the signal is still a member saying so, or somebody reading the Vercel logs. Linking currently works and is proven to: an item was linked 32 minutes after the fix, and all seven items are healthy.
- **Preview may break where production is fine.** Preview and local run on the Sandbox secret, and Sandbox entitlement for `recurring_transactions` is a separate question from the Production grant. If Sandbox refuses it, every preview deploy loses bank linking while production keeps working, which is the confusing direction for that failure to point.
- **Recurring detection only syncs when the member opens the app.** The daily cron does not run the recurring leg: `api/cron/daily-sync.ts` covers transactions, the net-worth snapshot, the score and merchant art, and nothing else. So streams go stale for a member who stops opening the app, and the panel shows a cache with no on-screen sign of its age. Not a defect, but it is a gap between what the cron implies and what it does.
- **The Settings "Refresh data now" button has been made honest, not proven fixed.** It appeared to do nothing while the Connections button worked, and #217 established that it could never have reported a failure: `runBackgroundSync()` swallows every error and returns an in-flight promise, so the button said "Done" whether or not anything happened. It calls `syncFinances()` directly now and reports what came back. The cause of the original symptom is still unknown, so a member pressing it and seeing nothing change is not yet a closed case; the Connections button is the one to trust in the meantime.
- **A merchant rule silently recategorizes charges, and the only guard against a bad one is the member noticing.** Precedence protects hand corrections (`user` beats `rule` beats `plaid`, covered by `check-category-precedence`), and rules are visible and removable since #217, but removing one does not undo the charges it already set, because Plaid's original classification is not kept: `plaid_category` holds the PRIMARY only. A rule made against the wrong merchant string is therefore a manual clean-up, one charge at a time.
- **Every category feature is one member deep.** Corrections, custom leaves, hidden categories, member-made groups, chosen emoji and merchant rules all shipped over three days against one production account, and the automated checks are pure-function checks with no database behind them. The three manual checks in `docs/PRODUCTION_CHECKS.md` passed on 2026-08-30, which covers a budget, a correction through a real Plaid replay, and a rule with its precedence, and nothing beyond that has been exercised by a second person.
- **A member's own category work sits on top of a sync that rewrites rows.** `transactions-sync` upserts with `merge-duplicates`, so anything the member owns has to be read and carried through the upsert on every run: corrections since #201, rules since #214. That pattern is now load-bearing in two places and a third writer that forgets it would quietly revert somebody's work, with the only symptom a category changing back days later.
- **Sharing was open by default until 2026-08-29, and that window is not hypothetical.** Migration 0020 closed every existing `partner_sharing_prefs` row as well as the column default, so nothing is exposed now, and since #195 that coarse flag no longer decides anything except the default scope for an account with no `account_shares` row, but any partnership formed before that date had the inviter's account balances visible to the partner from the moment they accepted, with no consent step. It is recorded here rather than only in the Decisions log because it is the kind of thing that has to be findable later.
- **The combined "Together" total double-counts an account both members linked separately.** Known, deliberate, and written into `api/partner.ts` beside the arithmetic. The number means "what the two of you have put into the shared space", not "what the two of you are worth", and it will read high for any couple with a genuinely joint account each of them has linked from their own login. Fixing it needs a per-account joint designation, which is an open loop.
- **The cron has fired but has never synced anything.** The 09:00 UTC run returned 200 on 2026-08-29 at 09:01:35 with `members_due: 0`, because the member had synced inside the 20-hour staleness window. Schedule and auth are proven; the code path that actually refreshes a stale member on a schedule is still unexercised in production. The failure mode is quiet: the job times out or errors and the only symptom is a gap in `net_worth_snapshots` that can never be filled afterwards, because the table is keyed by (user, day).
- **#193's update-mode Reconnect has never executed.** All seven connections are healthy, so the branch that repairs a dead item in place, rather than minting a duplicate beside it, has only been checked by reading and by a structural assertion that the token exchange sits after the update-mode return. If it is wrong the symptom is the exact thing it was built to prevent: two items for one bank, the dead one still feeding stale balances into net worth.
- **One of the seven balances is not a live read, permanently.** Item `5vyavBky` is **Carter Bank & Trust**, the member's primary checking, and `/accounts/balance/get` times out on every attempt, at 9s and then at 12s. #187 falls back to `/accounts/get`, so the figure is Plaid's own cached balance rather than nothing and rather than a stale copy of ours, and #192 says so on the Connections row. This is a known state, not a bug, but it should not be mistaken for a fix: Juniper cannot see a Carter balance newer than whatever Plaid last managed to fetch from the bank, and the underlying slowness is Carter's, not something the app can address.
- **Three different numbers describe "how much is connected", and they are easy to confuse.** Items (7, from the Plaid logs) are what Plaid bills and caps at 200. Institutions (at least six named) is what a member would say out loud, and is not derivable from the logs, because several accounts can sit behind one item. Accounts (13, the app bar pill) is what `linkedCount` sums. Quote items where the evidence is a log line, and never present the pill as an institution count.
- **Every Chase transaction row shows PENDING, including rows several days old.** Unverified. It may be Chase settling slowly, or it may be that stale pending rows are not being reconciled. Listed as a watch item, not a diagnosis.
- **The reconstructed net-worth trend was flat across about 73% of net worth and no longer is** (#256, run 2026-09-02). What remains is the residual inaccuracy that cannot be removed: the invested portion is reconstructed as today's holdings minus net contributions since, so it counts money added and not how the market moved, because Plaid reports today's prices and not past ones. Fees and taxes are not subtracted from investment flows either, so reconstructed invested balances run slightly high. Every reconstructed day is marked `estimated` and drawn dashed for exactly this reason.
- **There is no seeded data left in the app** (#186, #191), which closes this risk rather than moving it: `lib/shared-data.ts` and `sharing.tsx` are deleted, and all five shared surfaces read live endpoints. Recorded here because the rule is easy to re-break: a fixture added "just for a screenshot" would put a stranger's invented balances back on a money screen.
- **One surface and one whole shell are kept but unreachable** - Recommended is unrouted (#142), and nothing imports `pages/app-shell.tsx`, so the plan-detail surface and everything hanging off it (marketplace list, affiliate cards, projection charts, debt-list builder, next-action links, portfolio summary, the tap-first dialogue UI) is dead code that still typechecks and still builds. Deliberate and reversible, with un-hide conditions in each header comment.
- **Accessibility has been fixed on one surface, not audited across the app.** #190 gave plan cards and unstarted goal cards a real labelled button, which closes the specific defect logged last run. No sweep has been done over Overview, Transactions, Score, Credit, Connections, Ask or the shared surfaces, so the same pattern (a clickable div with a hover-only affordance) may well exist elsewhere.
- **Ask Juniper streams financial guidance with no safety pass and no disclaimers.** The surface is routed and grounded in the member's real figures. The prompt safety review and the financial-advice disclaimers named alongside it in Stage 11 have not been done.
- **The Credit page reads outside the finances seam** - a documented exception to the `CLAUDE.md` money-data-layer rule, not an oversight: `/api/finances` returns name, institution and balance per account, and utilization needs each card's `limit` from the stored Plaid snapshot. One surface therefore has its own data path.
- **Partner URLs, logos, and rates are demo placeholders** - every affiliate `url` is `example.com`, logos come from a favicon service, and projection rates are fixed constants. Regulated categories likely need specific disclosures and licensing. Do not launch monetized surfaces on these; they are plumbing and UX only.
- **Anthropic cost is uncapped** - no spending limit configured. Per-plan spend is low (structured steps make no LLM call), but Ask Juniper is an open-ended chat surface now, so a runaway loop or abuse could spike.
- **Plaid talks to real banks in production** - linked accounts are real people's real balances, held as an `access_token` in the server-only `plaid_items` table. Three live constraints: the tier caps Items at 200 per product, the Stage 6 compliance pair is not done so linking should stay narrow, and a mistake here has a real person's real balances behind it. Preview and Development stay on Sandbox by env scoping; `PLAID_REDIRECT_URI` is All Environments, so an OAuth link started from a preview deploy returns to the production origin and loses its queue.
- **Dark mode on the live app themes via the design system; verify per-page rather than assume** - the live shell picks up `.dark .jnpr`, so it follows the theme end to end. Marketing and auth pages sit outside the `.jnpr` surface and stay light by design. If an individual page looks off, verify and patch that page's tokens; it is not a known systemic gap.
- **Plaid service-role key is a high-value secret** - `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely and is what reads the `plaid_items` token store. It lives only in Vercel env; it must never reach the client bundle or a `VITE_`-prefixed var.
- **"Accounts I use" (onboarding) is still localStorage-only** - Plaid linked-institution names come from the server, but the onboarding-captured list they are merged with is client-side, so that half does not sync across devices.
- **Apps Script webhook secret is committed** - the growth pipeline's shared secret (`jnpr_whk_...`) is hard-coded in `juniper-sheet-webhook.gs`. Those files sit outside the git repo, but the secret is plaintext; rotate before any wider sharing.
- **Growth pipeline is out-of-repo** - the `.gs` files live in the parent directory and are not version-controlled with the app, so their state can drift silently.
- **Em-dash leakage** - Claude keeps emitting the character despite strict prompts; mitigated by a client-side strip in `displayContent()`, but any new surface that bypasses that helper will leak.
- **GRANT footgun for new tables** - SQL-migration-created tables do not auto-grant Data API access. New tables silently return 401 without `GRANT ... TO authenticated`. Baked into migrations 0002+ but easy to forget.
- **Env-var newline footgun** - past `Invalid header value` outages came from copy-pasted env vars with embedded newlines. `api/_env.ts` sanitizes on read; any new server-side env reader should use it.

## Notable debug lessons

Subtle enough to repeat, so worth keeping a section:

- **A link preview is built by a crawler that does not run JavaScript, so no client change can ever alter one.** An invite link previewed as the marketing card, and every fix that suggests itself in React is unreachable: `vercel.json` rewrites the route to a static `index.html` and the crawler reads that file. The answer is a function in front of the route. The second half of the lesson is that the function must FETCH the built shell rather than hold a copy of it, because a copy is a second `index.html` that goes stale on the hashed bundle name at the next deploy and silently drops the pre-paint theme script with it.
- **A string replace that matches nothing is a silent regression.** `setMeta` returns the html unchanged when the tag it was looking for is absent, so an unrelated edit to `index.html` would turn the whole preview back into the marketing card with no error anywhere. The caller therefore checks each of the six swaps. Any rewrite of somebody else's file needs to assert that it changed something.
- **One flag doing two jobs is right until the day only one of them applies.** `resolution=ignore-duplicates` on the net-worth backfill meant both "never overwrite an observation with a guess" and "never re-derive a guess", and the two came apart the moment a connection was relinked and the INPUTS to the reconstruction changed. Worth asking of any write mode: how many rules is this, and are they all still true.
- **A number predicted in a plan is not a verification, and it will be quoted as one.** The rebuild's expected counts were written down as 66 and 5 before it ran; the run reported 92 and 6, and the table agrees with the run, because the prediction was an addition error. The same thing happened to a utilization figure earlier in the week (2 percent written down where the arithmetic gives 1). Check a destructive operation's outcome in the data, and record the number the system reported rather than the one the plan expected.
- **`Math.abs()` on a balance destroys the one bit that mattered.** Plaid signs a credit-card balance negative when the account is in credit, and five call sites took the absolute value, so a $328 refund the issuer owed became $328 of debt, 7% utilization, a worse Score twice over and a smaller net worth. A sign on a money field is data, not noise.
- **A constant that claims in its comment to match a stylesheet will go stale, so derive it instead.** `FACE_H` said 124 with a comment claiming it matched `.cr-face-lg`, which is 149px at desktop, so every computed height in the holder was 25px short and cards hung below the pocket. It is derived from the ID-1 card aspect (85.60 x 53.98mm) now, which cannot drift, and the container is clipped so a layout error cannot spill.
- **Renaming a container silently unhooks every rule scoped to it.** Renaming `.cr-pocket` to `.cr-holder` detached ten descendant rules, including the two that hid the issuer name and the product name over card art, so labels that had been deliberately removed came straight back. Grep the class out of the stylesheet before renaming it, and re-render the states that the removed rules were about.
- **A temporal-dead-zone error typechecks cleanly and throws only once the feature is used.** `identityOf` calls `artOf`, and the manual branch was built before the no-linked-accounts early return, so with `artOf` declared where it had always sat, naming a hand-entered card threw a `ReferenceError`. It could only happen for a member who used the feature being added, which is the worst kind of ordering bug and is why the art map moved above its first use.
- **The clipboard mangled the data, not the migration.** Thirteen product names shipped with broken trademark symbols. `0032` and `0034` are correct UTF-8 (`C2 AE`, verified byte by byte); the macOS clipboard carried those bytes into the SQL editor, which read them as MacRoman. The repair therefore had to contain no byte above ASCII anywhere, including in its comments, because a repair carrying the sequence that got mangled arrives as broken as the thing it repairs: `chr(174)` and `chr(8480)` instead.
- **An add on is not a product, and a consent list only takes products.** `additional_consented_products` takes the same enum as `products`, so `recurring_transactions` was refused whether or not the Plaid account was entitled to it, and every `/link/token/create` returned 400 for a day. The rule being followed at the time ("add it once the entitlement lands, not before") guarded against naming an UNENTITLED product and therefore predicted the right failure for the wrong reason, which is worse than no rule, because it looked satisfied. The general shape: when a field is documented as taking an enum, check the enum, not the entitlement.
- **A client that collapses every failure to one message turns an outage into a feature flag.** `createLinkToken()` returned null for anything that was not a success, and the caller rendered "Account linking isn't enabled yet". That copy is honest for a 503 and a lie for a 400, so a total linking outage looked like a switch nobody had flipped, for a day, on the one call whose failure affects every member at once. Error copy has to be keyed on the status, and the highest-blast-radius call is where that is least optional.

- **A CHECK whose expression is NULL passes.** `->` on a key that is not there returns SQL NULL, `jsonb_typeof(NULL)` is NULL, and Postgres treats a NULL check expression as satisfied, so the first version of 0049's constraint accepted a layout with no `order` at all: a constraint written to require the key admitted the row missing it. `COALESCE(..., 'absent')` around every `jsonb_typeof` is the fix. Caught on a scratch Postgres by trying the missing-key cases, not by reading the SQL, which looked correct.
- **Three stale-closure bugs in one component, which is why the order, the hidden set and the dragged id are refs rather than state.** Each mutation can fire more than once before React re-renders, and reading the value out of the closure loses every write but the last: two shelf chips tapped in one tick put only ONE widget back, a held arrow key would have done the same, and a `pointerup` arriving in the same tick as its `pointerdown` read a stale null and left the board stuck mid-drag. The refs are updated synchronously so the second call in a tick sees the first. The rule that came out of it: state is for rendering, the write side reads refs.
- **A verification harness has to exercise the paths that differ, not the path that works.** The no-transaction-feed case is the one most members hit first, and it is where three of #252's rules bite at once: empty widgets collapse out of the live page, appear as dashed placeholders while arranging, and `ConnectNudge` sits outside the order entirely. None of that was proved until the fixture was flipped to have no feed. Same family as #188's harness, whose short merchant names meant no row could wrap, so a list that could not overflow certified a list that did.
- **A total rounded coarser than the rows above it disproves itself on screen.** `sumMonthly` rounded to whole dollars and the head rendered the result with `money2`, so a $7.92 annual fee beside a $6.98 subscription summed to $14.90 and displayed "$15.00", claiming a precision it did not have directly above the two figures that contradicted it. Rounding and formatting have to agree about precision, and the rule that falls out is to round at the last possible step, which is the renderer, not in the arithmetic feeding it. It only became visible when a real annual fee arrived with cents in its monthly conversion, which is the kind of defect a whole-dollar fixture hides.
- **A resolved value is right for a reader and wrong for a form.** `/api/subscriptions` resolves every field server-side, the member's answer where they gave one and the bank's otherwise, which is exactly what the list wants. Pre-filling the edit panel from that same value would have made "I chose $95" and "Plaid averaged $95" indistinguishable, so saving a cadence correction would have written Plaid's average in as an explicit expectation and killed the drift check the panel exists for. The fix is to send both layers and let the editor read the member's only, with the bank's figure as the placeholder, so an empty field keeps meaning "use what my bank says". Generalizes past this panel: any form over a merged view needs the unmerged layer, or its saves invent intent the member never expressed. Caught before commit by asking what a save would write, not by testing what the form displayed.
- **An index on an expression is not an index on the column.** Migration 0028 made merchant uniqueness case-insensitive with an index on `(user_id, lower(btrim(merchant)))`, and the endpoint upserted with `on_conflict=user_id,merchant`. Postgres requires the ON CONFLICT target to name an index over exactly those columns, so every insert raised 42P10 and no merchant rule could ever be saved. The fix is not a cleverer conflict target: put the normalized value in a column (`merchant_key`, migration 0029) so the thing the index is on is the thing the upsert names, and everything that matches on it, including DELETE and the sync, shares one definition.
- **A preview that stubs the network cannot catch a bug that lives in the shape of an index.** #214's picker and rule flow were verified against the real components with the endpoint stubbed, which is a good way to prove the UI and a useless way to prove a write. The rule bug survived review, a component preview and every automated check, and fell out of the first press of the button against production. Anything whose correctness lives in the database needs either the database or a check that reads the migration.
- **A total computed from a different copy of the same answer will disagree with the list it sits above, even after the arithmetic is right.** #195 fixed the shared total's arithmetic; #197 found that five components each held their own `usePartner` state, so the sheet could show an account shared while the Overview behind it still read private and zero. Two copies of one server answer is the same class of bug as two definitions of a lookup, and it had already caused #175 and #177 that week. When more than about three call sites need the same fetched state, the fix is one store, not careful prop passing.
- **Grep the reads before building on a plan that says the reads are safe.** `docs/CUSTOM_CATEGORIES.md` claimed renames were safe because rows point at ids. Rows carried ids and every endpoint still resolved by label, so the first rename would have dropped a member's history into Everything else and split a budget from its own spending. It cost one extra stage (#205) because it was caught by reading the selects before the rename shipped, and it would have cost a member's visible history if it had been caught after.
- **Write the new key before reading it, and keep the old path alive while you compare.** Category ids landed in migration 0024 and nothing read them for a whole stage, on purpose, so id and label could be checked against each other on real data before anything depended on either. The same ordering carried the resolver refactor (#204 changed the seam and not one answer, proved over the whole input domain against a fixture captured from the old module). It is slower and it is the only version of this that cannot move somebody's Score without telling them.
- **A generated file is a fact written twice, and the second copy loses its last line first.** `check-category-ids.ts` exists because migration 0024's mapping cannot import the taxonomy: it is SQL applied by hand, long after the deploy. It earned its place on the first run by catching a generated file that had lost its final entry to a missing newline, which would have left "Transfer in" with a null id forever, on every table.
- **A TDZ error typechecks cleanly and throws on first import.** `BUILTIN_TAXONOMY` was evaluated at module load, before the id helpers it calls were initialized. TypeScript was happy, the build was happy, and the module threw the first time anything imported it. Found by running the check, not by reading it, which is the argument for a script that executes the module over a review that reads it.
- **Unicode names things for archivists, not for people searching.** Searching "coffee" in the emoji picker returned nothing, because Unicode calls that emoji "hot beverage". CLDR's annotations are what every emoji keyboard actually searches, so the generator merges name, subgroup and CLDR keywords, which is the whole difference between a 73KB dataset and a 102KB one. Then "rent" matched "parent" and "transparent", so matching became per word prefix, which keeps "coff" finding coffee and drops the accidents. Both bugs came from using the feature, not from testing it.
- **Ask the machine what it can draw rather than asking a version table.** An emoji newer than the operating system renders as an empty box, and a grid with holes reads as a broken screen rather than as an old computer. Measuring each glyph against the missing-glyph width finds them in 17ms for 1,898 emoji, catches ZWJ sequences that fell apart (measurably wider than one emoji), and needs no table to maintain. Built-in defaults are still capped at Unicode 11.0, because nobody chose those and they have to draw everywhere.
- **A patch that applies half the response leaves the screen half wrong.** After a re-categorization the client applied the new category, group and kind and not the new emoji, so a charge moved to Coffee shops sat there wearing a shopping bag until the next page load. It was introduced the day icons shipped and invisible until somebody picked a category whose icon differed. When a server returns the whole new state of a row, apply the whole thing rather than the fields you were thinking about.
- **An empty thing created on purpose must not be filtered out with the empty things nobody wanted.** The picker drops empty groups so a search does not show bare headers, and a group a member has just created is empty by definition, so creating one looked like it had silently failed with no way to put anything in it. Empty groups are dropped only while searching now. Its sibling in the same PR: the group form offered a Hide that did nothing, since hiding is a leaf-level idea, and a control that is offered and ignored is worse than one that is absent.
- **A backfill that filters with `ilike` has to escape the pattern.** `%` and `_` are wildcards, so a rule made for a merchant like `PAYPAL *INST_XFER` would have matched more than itself, and a rule that files somebody else's charges is worse than one that misses. Escape at the point the pattern is built, and cover it where the matching rules already live.
- **A correction on a settled charge proves nothing about the sync.** A Plaid sync only rewrites transactions returned in `added` or `modified`, so correcting a three-week-old charge and finding it intact tests nothing: it was never touched. The two ways to get a real test are correcting a pending charge and waiting for it to post, or clearing one item's cursor so its history replays through the same upsert (safe, since the upsert dedupes on `plaid_transaction_id`). Written into `docs/PRODUCTION_CHECKS.md` because it is exactly the check somebody would otherwise perform on themselves and believe.
- **A total computed from a different source than the list it sits above will drift, and it can drift all the way to zero.** The shared Overview drew each side's accounts from per-account scopes and then computed the headline figure from a coarse pref and a full-account sum, so the two could never contradict each other loudly enough to be noticed: the list was right, the number was 0, and sharing an account changed the first and not the second. A figure that summarises a list has to be accumulated in the same pass over the same rows with the same skip rule, not derived independently and trusted to agree.
- **A fixture that cannot exhibit the bug will certify the bug.** #188's layout harness used short merchant names, so no row wrapped, so nothing overflowed, so a list that could not overflow passed a test about overflow and shipped a trapped scroll wheel (#189). When measuring a layout, build the fixture from the content that stresses it, the two-line merchant name and the thirteen-account column, not from tidy sample data.
- **Two timestamps on a row can both be wrong for one question.** "How old are these balances" looked answerable from `plaid_items` twice over and was not: `last_synced_at` is written by transactions-sync as well, and the one item that needed the answer syncs transactions perfectly while every balance call times out, so it read as freshly synced forever; `updated_at` is trigger-maintained and moves on any write, including the cursor. A timestamp is only trustworthy for the fact it is written beside. `balances_refreshed_at` is written in exactly one place, next to the snapshot it dates.
- **An early-return flag has to be read from the side you control.** Plaid's Link still hands back a public token in update mode, and exchanging it mints the duplicate item that update mode exists to prevent. The safe read is the repair flag the app put on its own queue, not the metadata coming back from the SDK.
- **A timeout is not a refusal, and treating them alike loses a whole strategy.** `/accounts/balance/get` timing out means the bank is slow; a dead item or a permissions error means the data genuinely is not available. Only the first has a good fallback (`/accounts/get`, Plaid's own cached balance, no round trip to the bank). Collapsing the two would either paper over real errors with stale figures or throw away the one bank that needed the fallback.
- **An empty-state branch can sit above the feature that fills it.** The Plans page returned "No plans yet" on `views.length === 0` before reaching the grid, so the goal cards added in #184 were unreachable for exactly the member they were built for, and the Overview half shipping fine made it look like a partial deploy rather than a bug. When adding a case to a list, check what returns before the list is rendered.
- **A shared frame that replaces children makes its own links unreachable.** `SharedPage` swapped in the blank canvas on every shared route while the space was empty, so following the canvas's "A bill" tile landed on Bills and rendered the canvas again, and the first bill could never be added, since the tab only appears once a bill exists. A frame should own one screen, not override every screen beneath it.
- **A permissive default is a decision nobody made, and it outlives the code that set it.** `share_balances` was `DEFAULT TRUE` in a migration and `true` again in a code default, and a third fallback in `scopeFor` agreed with both, so three independent layers all said "share it" and none of them had ever asked. The product copy said the opposite, in writing, in the same modal that created the partnership. When a default decides who sees somebody else's bank balances, the safe direction is the revoking one, and closing existing rows matters as much as changing the column: the flip alone would have protected only future partnerships.
- **A batch is a barrier, and a barrier is not concurrency.** Slicing items into rounds of six and awaiting each round means round two cannot start until the slowest bank in round one answers, so one twenty-second institution parks five idle workers and leaves six items untouched. The fix that looks done is only half done until the rounds become a pool: workers pulling from one cursor with nothing to wait on. Same shape as any "chunk and `Promise.all`" loop over a slow remote.
- **Budgeting the slow call is not budgeting the work.** `networth-snapshot` stopped starting new items at 18s and was still killed at 25, because the per-item work is a Plaid call plus two Supabase writes and only the Plaid call was inside the budget. A deadline has to reserve for the tail after the thing you were timing.
- **An incremental cursor means a feature added today never reaches yesterday's rows.** Merchant art shipped as a column filled by `/transactions/sync`, which by design never revisits a row, so a member whose history had already synced saw no art at all and would keep seeing none until each merchant charged them again. The general move is a lookup table keyed by the thing the data is a fact about (the merchant), not the row, so one write repairs the whole history without replaying the sync.
- **Returning early is a correctness requirement when the same function also deletes.** A recurring sync that reconciles against Plaid's answer deletes what Plaid no longer returns. Under a permissions error Plaid returns nothing, which is indistinguishable from "nothing recurring any more" if you keep going. The refusal has to short-circuit before the upsert and before the delete, not just be logged more quietly.
- **A card that renders art is not a card that asked for art.** The Overview transactions card showed monograms for weeks after merchant art shipped, and the cause was two layers up: `/api/finances` selected no `logo_url` and did no cache lookup, and the row component was the older `BrandTile`. When one surface disagrees with another about the same data, check what each one actually requested before debugging the renderer.

- **A fixed averaging window over a variable history inflates every ratio built on it.** `_finance-snapshot.ts` divided by a constant 90 days while a member had three weeks of transactions. That did not make the numbers noisy, it made them wrong in a consistent and flattering direction: emergency fund read 3x the months it actually covers, investing pace 3x the pace, debt load a third of the burden. The only figure that survived was savings rate, and only by luck, because it is a ratio of two numbers that were both a third too small. Any "per month" figure must divide by the history that exists, not the window that was requested.
- **A neutral placeholder inside a weighted score is not neutral.** `creditFactor` returned a flat 70 when there was no credit data. That was 10.5 points of a score presented to the member as their own, and because a 70 leaves the most headroom, it won the "biggest lever" ranking, so the app's single loudest instruction was to improve the one thing it had no data about. The fix is to drop an unmeasured component and renormalize the remaining weights, never to fill it in with a plausible number.
- **Reading the sign of a transaction is not reading what happened to the money.** `/api/finances` treated every outflow as spending and every inflow as income, so a transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent. The card payment was the worst case and the one nobody spots by eyeballing a total: the purchases it pays for already counted when they happened, so the member was billed twice in the same month for the same coffee. Only the category can tell a card payment from a car payment, and Plaid's *detailed* `personal_finance_category` is the level that carries it (the primary cannot). The blast radius reached past the dashboard, because spending and income feed the Score's savings rate and emergency-fund factor. Anything that classifies money by sign alone is wrong in the same way.
- **One AND-gate over two independent sources withholds both, and a loop that returns on first failure turns one bad item into an outage.** `api/finances.ts` required items AND transactions before returning anything, so real, already-stored balances were queued behind a feed that arrives minutes later and sometimes never. In the same PR: `networth-snapshot.ts` returned 502 the instant one item's balance call failed, and the snapshot rewrite sat inside that loop, so one broken connection meant nothing refreshed at all, while the caller discarded the response body and showed no error. Gate per section, isolate per item, and report what failed.
- **Deleting demo data makes degenerate shapes reachable for the first time.** Removing the mock layer meant `NetWorthChart` could finally receive a one-point series, a dead-flat series, and a negative series; it divided by `series.length - 1` and scaled bounds by 0.985/1.01, so all three produced NaN paths or inverted bounds. The same removal exposed a delta chip hardcoded to "up", safe only while the number came from a demo household that always rose. Seed data is not just wrong content, it is a shape filter hiding the empty and edge cases.
- **Check the account before the config** - a Plaid entitlement that looks inexplicably stuck is more likely the wrong account than a broken setting. Five months of "Production under review" were a different client ID's dashboard. Same shape applies to any per-account SaaS console.
- **Probe env changes without signing in** - `curl -X POST .../api/plaid/link-token -d '{}'` returns 401 when creds are present and 503 when `plaidConfigured()` is false, which distinguishes "Vercel has not picked up the env yet" from "auth is rejecting me" in one call. Plaid's real reason lands in the server log (`[plaid] link/token/create failed`), and the Vercel runtime-log query needs a short `since` window or it times out.
- **Env vars with embedded newlines** - `SUPABASE_ANON_KEY` had a `\n` at position 208 from a copy-paste. Node fetch headers reject CR/LF. `api/_env.ts` strips non-printable chars from all server-side env reads.
- **ES256 vs HS256** - Newer Supabase projects use asymmetric JWT signing keys (ES256). Legacy "JWT Secret" doesn't sign user tokens anymore. `api/_supabase-jwt.ts` checks `header.alg` and routes to JWKS (ES256) or HMAC (HS256) accordingly.
- **GRANT for raw-SQL tables** - Tables created via SQL migration don't auto-grant Data API access. Every new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated;` or every request returns silent 401.
- **Unescaped backticks in template literals** - `BASE` prompt had backticked angle brackets inside a backtick-delimited string. JS parser closed the template early and tried to interpret the rest as tagged template expressions ("X is not a function" at module load). Don't use backticks in prose inside backtick-delimited strings.
- **PostgREST OR filter quirks** - `or=(user_id.eq.X,partner_user_id.eq.X)` returned `[]` even when matching rows existed. Switched to two parallel queries + client-side merge.
- **Double-read of fetch response body** - `/api/plans` GET error path was reading `.text()` after `.json()`; fixed by buffering once and reusing.
