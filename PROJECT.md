## TL;DR

Juniper is a financial planning app for young individuals and families: net worth, spending, budgets, a proprietary 0 to 100 Juniper Score, and plans, all built from the member's own linked accounts. It runs at `www.juniperplan.com` on Plaid Production against a real member's real banks: **7 linked Plaid items** across at least six named institutions, reading **about $97k** of net worth. The phase is post-MVP iteration. **Twenty PRs landed between 2026-08-29 and 2026-08-31, #197 to #217, and nineteen of them have one subject: the member owns their categories.** Until this run the taxonomy was 11 groups over 46 leaves fixed at build time in `api/_categorize.ts`, and nothing a member did could touch it. Now a transaction's category can be corrected (#201), leaf categories can be added and renamed (#206, #207), hidden without being deleted (#208), given any emoji the machine can actually draw (#209, #210), groups can be created by the member (#213), and a merchant rule can file every charge from one merchant at once (#214). **The risky part of that shipped invisible.** Stages 1 to 3a of `docs/CUSTOM_CATEGORIES.md` changed nothing a member could see: stable category ids written but not read (#203, migration 0024), classification resolved per member through `taxonomyFor()` (#204), then reads keyed on the id rather than the label (#205), which is a stage the plan did not have, because the plan's claim that renames were already safe was wrong and was corrected in the same PR. **Budgets became configurable in the same run** (#199), on a third panel of the Transactions side rail, closing an open loop where `/api/budgets` had full CRUD and no caller at all; the panel deliberately ignores the range pills and always reads the current month. **Ops, all verified:** migrations 0024 through 0029 are applied to production (Finley, 2026-08-30), five automated checks live in `scripts/src/` and all five pass, and all three manual checks in `docs/PRODUCTION_CHECKS.md` passed on 2026-08-30 against real linked banks, including a category correction surviving a full replay of Chase's history. **That production pass found two bugs, both fixed in #216:** no merchant rule could ever be saved, because migration 0028's unique index was on an expression and the endpoint's `on_conflict` named the column (Postgres 42P10), and a corrected row kept its old icon. **One thing is known and unresolved:** the Settings "Refresh data now" button appeared to do nothing while the Connections one worked, and #217 made it able to report failure without proving the cause. Still open from earlier runs: the cron has fired but has never synced anything, #193's update-mode Reconnect has never executed, Charles Schwab needs a relink, and the Stage 6 compliance pair gates broad public linking.

## What it is

**The problem:** Money is spread across banks, cards, brokerages and loans, and there is no single honest view of where a person stands or what a decision would cost them. The tools that try either invent numbers to fill the gaps or stop at a budget.
**The solution:** A planning app that reads the member's own linked accounts and turns them into a net-worth trend, spending that means consumption rather than every outflow, a 0 to 100 Juniper Score built only from what it can actually measure, and plans funded from real balances. A partner can be invited as an optional layer on top; nothing crosses to them until it is explicitly shared.
**The user:** Individuals and families, late 20s to early 40s. Solo is the default experience, not a fallback.
**The value:** One place that tells a member the truth about their own money, with a next step attached to each number.

*This supersedes the original couples-first framing. The repositioning is Stage 0 in ROADMAP.md ("audience: individual-first, partner as a layer"), and as of #171 to #177 it is built: the personal app is complete on its own, and the shared space is a second workspace you switch into.*

## Where we are right now

**Categories stopped being something the code decided and became something the member owns.** The vocabulary was 11 groups over 46 leaf categories fixed at build time in `api/_categorize.ts`, which is what Monarch lets people change and Juniper did not. `docs/CUSTOM_CATEGORIES.md` (#202) scoped it against the code rather than sketching it, and the finding that shaped the whole thing is that the work was never the picker: `_categorize.ts` is a pure module with synchronous lookups, called at about twenty sites across six endpoints, several inside per-transaction loops, so per-member categories mean every one of those paths has to load a taxonomy first. Five stages were planned and six shipped, in order: stable ids (#203), a per-member resolver (#204), reads keyed on the id (#205, the stage the plan did not have), the `categories` table and endpoint (#206) with the picker on top (#207), hiding (#208), icons and the emoji picker (#209, #210), generated group colour (#212), and member-made groups (#213). Then merchant rules (#214), the production check doc (#215), and two rounds of fixing what the first real production pass found (#216, #217).

**The correction that would have vanished.** #201 made a transaction's category correctable by clicking the tag that already names it, and the part worth reviewing is not the picker: `transactions-sync` upserts with `resolution=merge-duplicates` and wrote `category_source: "plaid"` on every row it touched, so a correction would have survived only until Plaid next returned that transaction in `modified`, or until a failed sync replayed its cursor, and then it would have gone with no error and no trace. The sync now reads the member's overrides once per run and carries them through the upsert, still marked `user` so they keep winning, and a failure to read them is logged loudly rather than silently reverting somebody's work. Income and Transfers are offered alongside spending, because "this was a credit card payment, not shopping" is the correction most worth making: a card payment counted as spending bills the member twice for purchases that already counted when they happened.

**The plan was wrong about renames, and grepping the selects first is what caught it.** #202's stage 3 said renames were safe "because rows point at ids". Stage 1 had made rows CARRY ids and nothing READ them: every endpoint still resolved a stored row by its label, and `transactions.category` holds the label as it stood when the row was written. The first rename would therefore have dropped every earlier row into Everything else, shown two names for one category on one page, and split a budget from its own spending, leaving a limit reading zero with money plainly going out. #205 added `classify(categoryId, label)`, moved every read onto it, and corrected the doc in the same PR rather than leaving it to mislead the next reader.

**Two bugs came out of the first real production pass** (#216), and neither was reachable from a preview. No merchant rule could ever be saved: migration 0028 made uniqueness case-insensitive with an **expression** index on `(user_id, lower(btrim(merchant)))`, the endpoint upserted with `on_conflict=user_id,merchant`, and Postgres requires the ON CONFLICT target to name an index over exactly those columns, so every insert raised 42P10 and the member saw a 500 dressed as "Could not save that rule". Migration 0029 moves the normalization into a `merchant_key` column, so the thing the index is on is the thing the upsert names, and DELETE matches by key too. The second was smaller and the same shape as the first: the row patch after a re-categorization applied category, group and kind and not the emoji, so a charge moved to Coffee shops sat there wearing a shopping bag until the next page load. #216 also escaped `%` and `_` before the retroactive `ilike`, since a merchant like `PAYPAL *INST_XFER` would otherwise have matched more than itself.

**Known and unresolved: the Settings "Refresh data now" button.** It appeared to do nothing while the Connections button worked. #217 found that it went through `runBackgroundSync()`, which swallows every error and returns an in-flight promise rather than starting new work, so it reported "Done" whether or not anything happened. It calls `syncFinances()` directly now, the same as Connections, reports what came back, and holds its own busy flag. **That does not prove the cause of the symptom and is not claimed to.** What it does is turn an invisible failure into a visible one, which is the fastest route to the cause if it recurs. Use the Connections button meanwhile.

**Budgets are configurable, which closes a loop that had been open since Stage 3d.** `/api/budgets` has done full CRUD on per-category monthly limits for weeks with no client calling it, which is why #140 removed the Overview Edit button rather than leave it opening nothing. #199 adds the client half on a third panel of the Transactions side rail, beside Categories and Summary, next to the spending it bounds. **The panel deliberately ignores the range pills:** a budget is monthly, the page defaults to three months, and measuring a 3M or 1Y figure against a monthly limit produces a number nobody can act on, so every budget would read as wildly over the moment somebody pressed 1Y. It reads the current month from `/api/finances`, the one place that defines a month's spend, and names that month in its own header. #198 gave the Overview Budgets card an empty state first (it had mapped `budgets` with no length guard, so every linked member saw a titled box with nothing in it), and that empty state now links to `/app/transactions?panel=budgets`, so the nudge lands on the control it advertises. #200 then unpinned the spending donut from 210px and made it fluid to a 360px cap, because the side rail got nine rows taller and the circle stayed the same size in the middle of it.

**One copy of the shared overview, not five** (#197). Sharing an account turned the switch on in the sheet and left the account Private on the Overview behind it, with the combined total still zero. #195's arithmetic was right; the component drawing it had not heard. `usePartner` kept its own state per call site and five components call it, so refreshing one left the other four stale. It is a module store with subscribers now, concurrent first mounts share one request, and sign out clears it, because module state outlives a client-side route change and the next member signing in to the same tab would otherwise see the previous one's partner. That is the third bug in a day caused by two copies of one hook's state, after #175 and #177.

**Ops state.** Migrations 0024 through 0029 were applied to production by Finley on 2026-08-30, so all of 0001 to 0029 are applied with no duplicate numbers. Five automated checks live in `scripts/src/` and all five pass: `check-category-ids` (52 labels, 52 mapped in the migration, 52 distinct ids), `check-category-resolver` (798 classification cases against a fixture captured from the pre-refactor module), `check-member-categories` (32 taxonomy-merge cases), `check-category-emoji` (52 labels, every icon Unicode 11.0 or older), and `check-category-precedence` (10 cases). `gen-emoji-data.ts` sits beside them and regenerates the emoji dataset from Unicode and CLDR. All three manual checks in `docs/PRODUCTION_CHECKS.md` passed on 2026-08-30 against real linked banks: a budget saved and persisted with `category_id` populated; a category correction survived a full replay of Chase's history, where clearing the cursor brought all seven Chick-fil-A rows back with one identical `updated_at`, six of them still `rule` and one still `user`; and a merchant rule applied to 6 charges with precedence holding.

**Still open, and not re-litigated:** the Stage 6 compliance pair before broad public linking; the cron has fired and returned 200 but has never synced a stale member; #193's update-mode Reconnect has never executed, because it needs a genuinely dead item and all seven connections are healthy; the Charles Schwab relink, without which the reconstructed net-worth trend is flat across about 73% of net worth; Plaid's `recurring_transactions` add-on, still pending on Plaid's side; and affiliate URLs still `example.com`. Two watch items carry forward: no live partnership has yet moved the combined total, and every Chase transaction row shows PENDING, including rows several days old, which is still unverified either way.

**Fast health probe** without signing in: `curl -X POST https://juniper-api-server.vercel.app/api/plaid/link-token -d '{}'` returns **401** when credentials are present and **503** when `plaidConfigured()` is false, which is the quickest way to confirm Vercel picked up an env change. Plaid's real failure reason is logged server-side in `api/plaid/link-token.ts` (`[plaid] link/token/create failed`), readable through the Vercel MCP `get_runtime_logs` scoped to `environment: production` with a short `since` window (a wide window times out).

**Recorded elsewhere, not repeated here:** #195's combined-total fix, the sharing-default privacy defect closed by migration 0020, the Plaid Production resolution of 2026-08-25 and the demo-household teardown of 2026-08-26 all live in the Decisions log and Notable debug lessons, since they are settled history rather than current state.

- **Classification resolves per member, through one seam** *(PRs #204, #205, #206, `api/_categorize.ts`, `api/_taxonomy.ts`)*: `_categorize.ts` stopped exporting four module-level lookups and exports a `Taxonomy` instead, resolved once per request by `taxonomyFor(userId)`, with all six consumers migrated (finances, transactions, `_finance-snapshot`, subscriptions and both Plaid sync paths) and the two sync row builders taking the taxonomy as an argument rather than reaching for a module import. The free functions were un-exported rather than left beside the resolver, because two ways to answer "what group is this" is how the answers come to differ. Reads then moved onto `classify(categoryId, label)`, id first and stored label second, returning the CURRENT display label with its group and kind, so a category renamed halfway through a range is one bucket rather than two and a budget cannot be split from its own spending. `groupOf` and `kindOf` remain for callers that genuinely hold only a label, and carry a doc comment saying that reading a stored row with them is a bug waiting for the first rename. `taxonomyFor` lives in `api/_taxonomy.ts` and not in `_categorize.ts`, which is documented as pure and I/O-free precisely so the sync, the read endpoints and the score snapshot can share it: a Supabase read inside it would drag the service-role client into every one of them, the same split as `_networth-walk.ts` beside its endpoint. A member with no category rows gets `BUILTIN_TAXONOMY` itself, so the common path allocates nothing, and a failed read degrades to the built-ins rather than 500ing a dashboard. **Why the care:** `_finance-snapshot.ts` feeds the Juniper Score and `score_history` is keyed by (user, day), so a day written from a wrong classification cannot be quietly recomputed later
- **`categories` holds only what a member added or changed** *(PR #206, migration 0025, `api/categories.ts`)*: a layer over the built-in table rather than a copy per account, so a member who never touches categories writes no rows and a built-in improved later improves for everybody instead of being frozen at signup. Two row shapes, told apart by whether `category_id` names a built-in: a created leaf carries its group, a renamed built-in keeps the group it already had. `buildTaxonomy` takes explicit ids rather than deriving them from labels, because a rename keeps `c_coffee_shops`, which is the entire reason stage 1 put ids on three tables. `/api/categories` does GET, create, rename, hide and delete, and exists for two refusals rather than as CRUD: **a leaf cannot be re-parented**, since moving one into a group of another kind would reclassify a whole history and move the member's Score with no visible cause, and **a leaf in use cannot be deleted**, with the refusal naming the count, since deleting it would leave rows pointing at an id nothing resolves. PATCH covers rename and hide together, because they are the same row and merge-duplicates replaces the whole row, so sending one half has to carry the other; clearing both deletes the row, which makes unhide the true inverse of hide. Leaves only: groups a member creates are handled in #213 and are always `spend`
- **Hidden is not deleted** *(PR #208, migration 0026)*: a hidden category leaves the picker and keeps resolving, so every charge already filed there still names it, still lands in its group and still counts toward a budget on it. Every lookup in `buildTaxonomy` takes hidden leaves except `writableLabels`, and that single omission is the whole definition. It is also the only version of "get this out of my way" that survives the sync, since `_categorize.ts` maps Plaid's own categories onto built-in labels and knows nothing about what a member has hidden, so a truly deleted built-in would come back on the next sync as a label nothing resolves. 0026 adds `archived` and makes `name` nullable, because a row that only hides a built-in has no name to give it, with a CHECK stopping a row that neither renames nor hides
- **Member-made groups, always spending, slotted before the catch-all** *(PR #213, `api/finances.ts`)*: a group decides whether its money counts as spending at all and `_finance-snapshot.ts` feeds the Score from exactly that, so the kind is not a member's choice; Income and Transfers stay built-in and creating a leaf inside either remains the visible route to a category that is not spending. A member's group is slotted **before** Everything else, because the catch-all reads last on a donut and a group somebody made is a real category of spending. A built-in group still cannot be renamed or deleted, since its label is what every row stored at group precision resolves through and every group-level budget is keyed by it. A group holding categories cannot be deleted, and the refusal names the count. `SPEND_GROUPS` is deleted from the client: it was a fixed list of nine, which stopped being true the moment a member could make a tenth, so `/api/finances` sends the member's own groups and the budgets panel reads those
- **A correction survives the sync, which is the part that would have failed silently** *(PR #201, `api/plaid/transactions-sync.ts`)*: the schema has carried `category_source = 'user'` since migration 0008 and nothing ever wrote one. The sync upserts with `resolution=merge-duplicates` and wrote `category_source: "plaid"` on every row it touched, so a correction would have survived only until Plaid next returned that transaction in `modified`, or until a failed sync replayed its cursor, and would then have vanished with no error and no trace. The sync now reads this member's overrides once per run and carries them through the upsert, still marked `user` so they keep winning, and a failure to read them is logged loudly rather than silently reverting the member's work. No migration was needed: the column, its CHECK, the GRANT and the owner RLS policy all landed in 0008
- **Merchant rules, and a precedence decision in its own module** *(PRs #214, #216, migrations 0028 and 0029, `api/merchant-rules.ts`, `api/_category-precedence.ts`)*: "always categorize this merchant as this category", applied to the charges already there and to everything that arrives after. **Precedence is user, then rule, then plaid**, because a rule is a statement about a merchant and a correction is a statement about one charge, so the more specific one wins; otherwise a member who rules "Amazon is Shopping" and then files a single Amazon charge under Groceries would watch their own rule undo it on the next sync. The retroactive update expresses the same rule as a filter, skipping rows the member corrected by hand. The decision is a pure function in its own module because it is the code that quietly reverts a member's work when it is wrong, and it has been wrong before. Matching is on Plaid's merchant name, lowercased and space-collapsed, and nothing cleverer: stripping store numbers and processor prefixes ("SQ *BLUE BOTTLE #241") is the kind of guess that catches a merchant the member never named, and a rule that files the wrong charge is worse than one that misses. A charge Plaid gave no merchant for cannot be ruled on. Deleting a rule does not undo it, and the endpoint says so. **0029 exists because 0028 could never save a rule:** the unique index was on an expression, `lower(btrim(merchant))`, while the endpoint upserted with `on_conflict=user_id,merchant`, and Postgres requires the ON CONFLICT target to name an index over exactly those columns, so every insert raised 42P10. 0029 moves the normalization into a `merchant_key` column, which also puts the key the sync matches on into the row instead of recomputing it per read, and DELETE matches by key so removing a rule made for "AMAZON" does not report nothing to remove because the row says "Amazon". Both reads in the sync degrade loudly rather than silently: a failure to read rules means new charges follow Plaid rather than the member, which is wrong but recoverable, where skipping the sync strands the whole feed
- **Category ids, written before they were read** *(PR #203, migration 0024)*: three tables identify a category by its TEXT label and `budgets` has a unique index on (user_id, category, period), so a rename would have orphaned the member's own limit with no error. `_categorize.ts` gained a stable id for every built-in group and leaf plus `categoryIdOf(label)`, slugs rather than UUIDs because a category id is read by a human far more often than by a machine, prefixed `g_` and `c_` because five labels (Shopping, Transportation, Utilities & bills, Groceries & dining, Everything else) name both a group and a leaf inside it. 0024 adds `category_id` to `transactions`, `budgets` and `recurring_streams` and backfills each from the same mapping; four write paths populate it alongside the label. **Nothing read it in that PR**, deliberately, so the id and the label could be compared on real data before anything depended on either. An unrecognized label gets a null id rather than a fallback, since inventing one would assert a classification `groupOf()` never made
- **The combined "Together" total is summed from the same rows the list is built from** *(PR #195, `api/partner.ts`)*: the total used to read `theirs.share_balances ? await memberNetWorth(partnerId) : 0`, where `memberNetWorth` summed every account a member had and the coarse pref decided whether any of it counted. Per-account scope never entered the number, so after migration 0020 closed that flag the partner contributed exactly 0 whatever they shared, and had the flag been true the total would have counted accounts explicitly marked private. `youNW` and `partnerNW` are now accumulated inside the same loops that build the account rows, one skip rule for both, so the figure cannot disagree with the list under it, and `memberNetWorth` was deleted with no other caller. **Both members see the same figure**, what each has put into the shared space; summing the caller's own accounts in full would have given the two of them different totals for one shared page. The coarse `share_balances` pref survives in exactly one job, as the default in `scopeFor` for an account with no `account_shares` row, which since 0020 means private. `set-account-share` writes `"shared"` or `"private"` and still accepts `"balance"` for rows that predate #195. **Known and deliberately unfixed, recorded as a comment beside the arithmetic:** an account both members linked separately is counted twice, once on each side, so this total is "what the two of you have put in", not "what the two of you are worth"
- **A daily cron, so a member who never opens the app still has a history** *(PR #167, `api/cron/daily-sync.ts`)*: `net_worth_snapshots` and `score_history` are keyed by (user, day), so a day nobody wrote is a day nobody can write later, and until this landed the only trigger was a member opening the dashboard. The awkward part is that the three sync endpoints authenticate a member's JWT and a cron holds none. Rather than teach three member-facing endpoints a second way to be trusted, each was split at the point the user id is known: a handler that establishes the caller, and a `run*(userId)` that does the work. The cron calls those, so a scheduled refresh and a member-triggered one are the same code. It refuses anything without `Authorization: Bearer $CRON_SECRET`, compared in constant time, and refuses everyone including Vercel when that variable is unset. Members stale past 20 hours are served stalest first, to an 18s deadline, and it will not start a member it cannot finish. Scheduled `0 9 * * *` in `vercel.json`
- **Backfill merchant art without replaying the sync cursor** *(PR #178, `api/plaid/merchant-art-backfill.ts`)*: `/transactions/sync` is incremental by cursor and never revisits a stored row, so #158's art only worked forward. This fills `merchant_logos` from `/transactions/get` over a 180-day window, leaving sync state alone, and `api/transactions.ts` resolves a row as `t.logo_url ?? logoOf.get(t.merchant_name)`, so one merchant-level upsert covers a whole history. It asks the database which merchants are missing first and returns without calling Plaid when none are, which is what makes it safe on every refresh and from the cron
- **One refusing bank costs its own balance, not the day, and not forever** *(PRs #180, #183, #187, `api/plaid/networth-snapshot.ts`)*: an item that fails now contributes its last known balances from the stored `plaid_items.accounts` snapshot and the row is written with `estimated = true`, rather than the whole day's trend point being dropped. Skipping survives only for an item that has never refreshed at all, where there is no last known balance to carry. The run also reserves `WRITE_RESERVE_MS` (4s) of its 18s deadline for the tail after the Plaid call, since `refreshItem` is a Plaid call plus two Supabase writes and only the call had been inside the budget, which is why the function was still being killed at 25s. **#183 put a ceiling on the carry at seven days** (`CARRY_MAX_DAYS`), because an item that never comes back would otherwise fold a frozen number into every future total, presented as today's, and the only signal would be a dashed point indistinguishable from a legitimate reconstruction; past the cutoff the item stops contributing and the day is skipped honestly, which is what the original rule protected. An item that never refreshed and one whose balances went stale are counted apart in the log, and `carry_expired` rides on the response so a trend that stops receiving points explains itself outside the logs. **#187 then made the slow bank answer at all:** on a timeout only, never on a dead item or a permissions error, the endpoint falls back to `/accounts/get`, which returns the balance Plaid already holds with no round trip to the bank, in about a second. The fallback is budgeted from the run's remaining time rather than the budget of the call that just timed out. `balances_refreshed_at` (0022) is written here and nowhere else, beside the snapshot it dates, and `balances_from_cache` (0023) records which of the two paths wrote it
- **Plaid calls have deadlines, and the pool has no barrier** *(PRs #152, #162, `api/_pool.ts`)*: a member with twelve institutions was getting a 504 on `/api/plaid/networth-snapshot`, because the loop was serial and `/accounts/balance/get` goes to the bank for a live balance, so its latency is the bank's. #152 batched six at a time; #162 finished the job, because a batch is a barrier and one twenty-second bank parked five idle workers. `mapPool` is six workers pulling from one cursor, pure and importing nothing. Every `plaidFetch` now carries a timeout (15s default, tighter when a caller is walking a whole connection list), a timeout returns `JUNIPER_REQUEST_TIMEOUT` which is deliberately not a dead-item code, and a transport failure comes back as a result rather than a throw, because one rejection inside `Promise.all` abandons the others mid-flight
- **Recurring detection waits quietly for its entitlement** *(PRs #155, #165, `api/plaid/recurring-sync.ts`)*: `recurring_transactions` is a separate Plaid add-on, not entitled under Transactions, and production settled it on 2026-08-28 with every item returning 400 `INVALID_PRODUCT`. The endpoint used to make that as loud as possible, six error lines and a 502 every six hours on a background leg whose body the caller drops. The first item to hit an entitlement refusal now sets a flag, every queued item skips its call, one warning is written, and the endpoint answers 200 with `available: false`. Critically it returns **before** the upsert and before the delete: falling through with zero rows would read as "Plaid no longer detects any of your streams" and wipe the member's cached list on the strength of a permissions error. Per-item failures are untouched
- **Persisted per-item sync state** *(PR #156, migration 0017)*: `needs_relink` used to be computed inside a sync the member had just triggered and then thrown away, so a page load could not tell a connection whose login had expired from one that was simply quiet. `plaid_items` now carries `last_synced_at`, `last_error_code` and `last_error_at`, written by all three sync endpoints through one shared helper (`api/_item-sync-state.ts`). Only dead-item codes are recorded: a transient failure resolves on the next run, and surfacing those would train people to ignore the one message that matters
- **Plaid edge endpoints** call Plaid directly over `fetch` (no SDK, edge-safe): `link-token` (creates a Link token), `exchange` (public token → access token, stored server-side), `accounts` (returns sanitized snapshots), `remove` (unlinks). Helpers `api/_plaid.ts` (Plaid fetch wrapper) and `api/_supabase-admin.ts` (service-role client). The Plaid `access_token` never leaves the server
- **Spending means consumption, and every category means something** *(PR #136, `api/_categorize.ts`)*: `/api/finances` used to read only the sign of a transaction amount, so every outflow was spending and every inflow was income. A transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent, and the card payment was the worst of it, because the purchases behind it already counted when they happened, so the member was billed twice in the same month. `_categorize.ts` is now the single taxonomy table: **11 groups** (9 spend, 1 income, 1 transfer) over **46 leaf categories**, driven by Plaid's *detailed* `personal_finance_category` with the primary as a floor. Since #206 to #213 that table is the built-in layer a member's own categories and groups sit on top of, resolved per request by `taxonomyFor()`, and the module itself is documented as pure and I/O-free so the sync, the read endpoints and the score snapshot can all share it. Each group carries a `kind`, and three rules follow from it: `transfer` is ignored entirely, `income` is netted from its own categories, and `spend` is summed **signed**, so a refund reduces the category it came back to instead of masquerading as income. Groups are derived at read time and never stored, and `spent` is *defined as* the sum of the breakdown, so the card header, the donut center, and the cashflow strip cannot disagree. The same three rules run in `api/_finance-snapshot.ts`, which is why this reaches past the dashboard: those two numbers feed the Juniper Score's savings rate and emergency-fund factor. On the worked example in the PR, a July went from $5,844 spent / $6,535 income to $3,384 / $6,400
- **Balances ship without waiting on transactions, and one dead item no longer blocks a refresh** *(PR #132)*: `api/finances.ts` gates per section instead of behind one AND-gate. `netWorth` and `accounts` ship the moment any account source exists (Plaid snapshot or `manual_accounts`); `cashflow`, `spending`, `budgets`, and `transactions` ship only once transaction rows exist, and absent sections are omitted rather than zero-filled, because a zero would overwrite a real figure the member gave us. `{ linked: false }` now means all three sources are empty, and a `hasTransactions` boolean rides along so the client gates on a real signal. Both sync endpoints isolate per item: a refused item is logged with its Plaid error code, recorded in `failures[]` (flagged `needs_relink` for `ITEM_LOGIN_REQUIRED` and `INVALID_ACCESS_TOKEN`), and skipped, with a non-200 only when every item fails; `transactions-sync` deliberately does not persist a cursor for a failed item, since replay is safe. A partial run refreshes per-item balances but reports `snapshot_skipped` and writes no trend point. Client side, `syncFinancesUntilTransactions()` retries only the transactions leg with bounded exponential backoff, so a link whose first pull is not ready yet still lands
- **`api/plaid/institutions-search.ts` and `api/plaid/institution-logos.ts`** *(PRs #129, #133, #144)*: search POSTs Plaid `/institutions/search` filtered by `PLAID_PRODUCTS`, so nothing offered can fail at link time, and returns `institution_id`, `name`, `oauth`, `routing_number`, plus `logo` and `primary_color` from `include_optional_metadata`. The logo endpoint takes institution ids **only** from the caller's own `plaid_items` rows via the service-role client, deduped, oldest first, capped at 25, so it cannot be used as an authenticated Plaid enumeration proxy; a Plaid refusal is logged and skipped rather than failing the request, and the response carries `Cache-Control: private, max-age=604800`
- **The Juniper Score is computed off the history the member actually has** *(PR #146, `api/_score.ts` + `api/_finance-snapshot.ts`, mirrored in `src/lib/score.ts`)*. `_finance-snapshot.ts` used to divide income and spending by a constant three months (`WINDOW_DAYS / 30`) regardless of how much history existed; it now divides by the days the transactions actually span, floored at 14 (`MIN_COVERED_DAYS`) and capped at the 90-day window (`coveredDays`). `creditFactor` no longer returns a flat 70 when there is no credit data: it returns `null`, `computeScore` filters it out, and the remaining weights renormalize to sum to 1, so each factor's published "% of score" is what it actually is. Where the data does exist it is used: revolving utilization is computed from linked cards that report a `limit`, counting only those cards so a limitless card cannot inflate the ratio, and before manual balances fold in
- **Net-worth backfill** *(PR #147)*: `api/plaid/networth-backfill.ts` walks backward from today's balances through the transactions that moved them (`cash(day-1) = cash(day) + that day's depository total`, `owed(day-1) = owed(day) - that day's credit total`, `invest(day-1) = invest(day) - external inflow`). The pure arithmetic lives in `api/_networth-walk.ts`, split out following the `_score.ts` convention, because the signs are the whole correctness story. Investments cannot be reconstructed exactly (market movement is not a transaction and Plaid has no historical price feed), so the invested balance is today's holdings minus net contributions since, read from `/investments/transactions/get`. Flows are classified by **subtype, not type**, because Plaid files `contribution` under `type: buy` and `distribution` under `type: sell`; direction also comes from the subtype, because Plaid signs a combined contribution-and-purchase positive like a buy. `BACKFILL_MAX_DAYS` is 365. Rows are written with `Prefer: resolution=ignore-duplicates`, so a day Juniper actually recorded always beats a reconstruction
- `api/plaid/link-token.ts` sends `additional_consented_products: ["investments"]` (PR #144), so items linked from that point on can serve `/investments/transactions/get`. ## Decisions log

- **2026-08-31, the Settings refresh button is made able to report failure, which is not the same as fixing it** - it went through `runBackgroundSync()`, which swallows every error and returns an in-flight promise rather than starting new work, so it reported "Done" whether or not anything happened, and it borrowed the context's `syncing` flag, which is true only for the automatic sync and left the button disabled while something it had not started was running. It calls `syncFinances()` directly now, the same as the Connections button, reports connections needing a relink, a run that refreshed nothing, or a throw, and holds its own busy flag. Swallowing errors is still right for a refresh nobody asked for and wrong for a control somebody pressed. **The cause of the reported symptom is not proven and is not claimed to be.** Rejected: guessing at a fix and closing the item, which would have left the next occurrence just as invisible.
- **2026-08-30, precedence is user, then rule, then plaid, and the decision lives in its own pure module** - a rule is a statement about a merchant and a correction is a statement about one charge, so the more specific one wins; otherwise a member who rules "Amazon is Shopping" and then files a single Amazon charge under Groceries would watch their own rule undo it on the next sync. The retroactive apply expresses the same rule as a filter, skipping rows the member corrected by hand. `api/_category-precedence.ts` is separate because it is the code that quietly reverts a member's work when it is wrong, and it has been wrong before: until #201 the sync wrote `category_source: "plaid"` over everything. All eight combinations are covered without a database, a Plaid account or a session. Rejected: matching merchants more cleverly than lowercase and space-collapse, because stripping store numbers and processor prefixes ("SQ *BLUE BOTTLE #241") catches merchants the member never named, and a rule that files the wrong charge is worse than one that misses. Also decided: deleting a rule does not undo the charges it set, and the endpoint says so, because reverting them would mean restoring Plaid's original classification and `plaid_category` holds Plaid's PRIMARY only.
- **2026-08-30, a member's group is always spending, and is slotted before Everything else** - a group decides whether its money counts as spending at all, and `_finance-snapshot.ts` feeds the Juniper Score from exactly that, so letting a member choose the kind would move their score with no visible cause. Income and Transfers & payments stay built-in, and creating a leaf inside either remains the visible route to a category that is not spending; the row says "spending" rather than leaving it to be found out. The slot matters too: Everything else is the catch-all and reads last on a donut, so a group somebody made belongs among the real categories rather than after the bucket for things that fit nowhere. A built-in group still cannot be renamed or deleted, because its label is what every row stored at group precision resolves through and every group-level budget is keyed by it. ## Risks & known issues

- **The Settings "Refresh data now" button has been made honest, not proven fixed.** It appeared to do nothing while the Connections button worked, and #217 established that it could never have reported a failure: `runBackgroundSync()` swallows every error and returns an in-flight promise, so the button said "Done" whether or not anything happened. It calls `syncFinances()` directly now and reports what came back. The cause of the original symptom is still unknown, so a member pressing it and seeing nothing change is not yet a closed case; the Connections button is the one to trust in the meantime.
- **A merchant rule silently recategorizes charges, and the only guard against a bad one is the member noticing.** Precedence protects hand corrections (`user` beats `rule` beats `plaid`, covered by `check-category-precedence`), and rules are visible and removable since #217, but removing one does not undo the charges it already set, because Plaid's original classification is not kept: `plaid_category` holds the PRIMARY only. A rule made against the wrong merchant string is therefore a manual clean-up, one charge at a time.
- **Every category feature is one member deep.** Corrections, custom leaves, hidden categories, member-made groups, chosen emoji and merchant rules all shipped over three days against one production account, and the automated checks are pure-function checks with no database behind them. The three manual checks in `docs/PRODUCTION_CHECKS.md` passed on 2026-08-30, which covers a budget, a correction through a real Plaid replay, and a rule with its precedence, and nothing beyond that has been exercised by a second person.
- **A member's own category work sits on top of a sync that rewrites rows.** `transactions-sync` upserts with `merge-duplicates`, so anything the member owns has to be read and carried through the upsert on every run: corrections since #201, rules since #214. That pattern is now load-bearing in two places and a third writer that forgets it would quietly revert somebody's work, with the only symptom a category changing back days later.
- **Sharing was open by default until 2026-08-29, and that window is not hypothetical.** Migration 0020 closed every existing `partner_sharing_prefs` row as well as the column default, so nothing is exposed now, and since #195 that coarse flag no longer decides anything except the default scope for an account with no `account_shares` row, but any partnership formed before that date had the inviter's account balances visible to the partner from the moment they accepted, with no consent step. It is recorded here rather than only in the Decisions log because it is the kind of thing that has to be findable later.
- **The combined "Together" total double-counts an account both members linked separately.** Known, deliberate, and written into `api/partner.ts` beside the arithmetic. The number means "what the two of you have put into the shared space", not "what the two of you are worth", and it will read high for any couple with a genuinely joint account each of them has linked from their own login. Fixing it needs a per-account joint designation, which is an open loop.
- **The cron has fired but has never synced anything.** The 09:00 UTC run returned 200 on 2026-08-29 at 09:01:35 with `members_due: 0`, because the member had synced inside the 20-hour staleness window. Schedule and auth are proven; the code path that actually refreshes a stale member on a schedule is still unexercised in production. The failure mode is quiet: the job times out or errors and the only symptom is a gap in `net_worth_snapshots` that can never be filled afterwards, because the table is keyed by (user, day).
- **#193's update-mode Reconnect has never executed.** All seven connections are healthy, so the branch that repairs a dead item in place, rather than minting a duplicate beside it, has only been checked by reading and by a structural assertion that the token exchange sits after the update-mode return. If it is wrong the symptom is the exact thing it was built to prevent: two items for one bank, the dead one still feeding stale balances into net worth.
- **One of the seven balances is not a live read, permanently.** Item `5vyavBky` is **Carter Bank & Trust**, the member's primary checking, and `/accounts/balance/get` times out on every attempt, at 9s and then at 12s. #187 falls back to `/accounts/get`, so the figure is Plaid's own cached balance rather than nothing and rather than a stale copy of ours, and #192 says so on the Connections row. This is a known state, not a bug, but it should not be mistaken for a fix: Juniper cannot see a Carter balance newer than whatever Plaid last managed to fetch from the bank, and the underlying slowness is Carter's, not something the app can address.
- **Three different numbers describe "how much is connected", and they are easy to confuse.** Items (7, from the Plaid logs) are what Plaid bills and caps at 200. Institutions (at least six named) is what a member would say out loud, and is not derivable from the logs, because several accounts can sit behind one item. Accounts (13, the app bar pill) is what `linkedCount` sums. Quote items where the evidence is a log line, and never present the pill as an institution count.
- **Every Chase transaction row shows PENDING, including rows several days old.** Unverified. It may be Chase settling slowly, or it may be that stale pending rows are not being reconciled. Listed as a watch item, not a diagnosis.
- **The reconstructed net-worth trend is flat across about 73% of net worth** until Charles Schwab is relinked, because that item never consented to Investments and cannot serve `/investments/transactions/get`.
- **There is no seeded data left in the app** (#186, #191), which closes this risk rather than moving it: `lib/shared-data.ts` and `sharing.tsx` are deleted, and all five shared surfaces read live endpoints. Recorded here because the rule is easy to re-break: a fixture added "just for a screenshot" would put a stranger's invented balances back on a money screen.

Deliberate and reversible, with un-hide conditions in each header comment.

No sweep has been done over Overview, Transactions, Score, Credit, Connections, Ask or the shared surfaces, so the same pattern (a clickable div with a hover-only affordance) may well exist elsewhere.

One surface therefore has its own data path.
- **Partner URLs, logos, and rates are demo placeholders** - every affiliate `url` is `example.com`, logos come from a favicon service, and projection rates are fixed constants. Regulated categories likely need specific disclosures and licensing. Do not launch monetized surfaces on these; they are plumbing and UX only.
- **Anthropic cost is uncapped** - no spending limit configured. Per-plan spend is low (structured steps make no LLM call), but Ask Juniper is an open-ended chat surface now, so a runaway loop or abuse could spike.
- **Plaid talks to real banks in production** - linked accounts are real people's real balances, held as an `access_token` in the server-only `plaid_items` table. Three live constraints: the tier caps Items at 200 per product, the Stage 6 compliance pair is not done so linking should stay narrow, and a mistake here has a real person's real balances behind it. Preview and Development stay on Sandbox by env scoping; `PLAID_REDIRECT_URI` is All Environments, so an OAuth link started from a preview deploy returns to the production origin and loses its queue.
- **Dark mode on the live app themes via the design system; verify per-page rather than assume** - the live shell picks up `.dark .jnpr`, so it follows the theme end to end. Marketing and auth pages sit outside the `.jnpr` surface and stay light by design. If an individual page looks off, verify and patch that page's tokens; it is not a known systemic gap.
- **Plaid service-role key is a high-value secret** - `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely and is what reads the `plaid_items` token store. It lives only in Vercel env; it must never reach the client bundle or a `VITE_`-prefixed var.
- **"Accounts I use" (onboarding) is still localStorage-only** - Plaid linked-institution names come from the server, but the onboarding-captured list they are merged with is client-side, so that half does not sync across devices.
- **Apps Script webhook secret is committed** - the growth pipeline's shared secret (`jnpr_whk_...`) is hard-coded in `juniper-sheet-webhook.gs`. Those files sit outside the git repo, but the secret is plaintext; rotate before any wider sharing.
- **Growth pipeline is out-of-repo** - the `.gs` files live in the parent directory and are not version-controlled with the app, so their state can drift silently.
- **Em-dash leakage** - Claude keeps emitting the character despite strict prompts; mitigated by a client-side strip in `displayContent()`, but any new surface that bypasses that helper will leak.
- **GRANT footgun for new tables** - SQL-migration-created tables do not auto-grant Data API access. New tables silently return 401 without `GRANT ... TO authenticated`. Baked into migrations 0002+ but easy to forget.
- **Env-var newline footgun** - past `Invalid header value` outages came from copy-pasted env vars with embedded newlines. `api/_env.ts` sanitizes on read; any new server-side env reader should use it.

## Notable debug lessons

Subtle enough to repeat, so worth keeping a section:

- **An index on an expression is not an index on the column.** Migration 0028 made merchant uniqueness case-insensitive with an index on `(user_id, lower(btrim(merchant)))`, and the endpoint upserted with `on_conflict=user_id,merchant`. Postgres requires the ON CONFLICT target to name an index over exactly those columns, so every insert raised 42P10 and no merchant rule could ever be saved. The fix is not a cleverer conflict target: put the normalized value in a column (`merchant_key`, migration 0029) so the thing the index is on is the thing the upsert names, and everything that matches on it, including DELETE and the sync, shares one definition.
- **A preview that stubs the network cannot catch a bug that lives in the shape of an index.** #214's picker and rule flow were verified against the real components with the endpoint stubbed, which is a good way to prove the UI and a useless way to prove a write. The rule bug survived review, a component preview and every automated check, and fell out of the first press of the button against production. Anything whose correctness lives in the database needs either the database or a check that reads the migration.
- **A total computed from a different copy of the same answer will disagree with the list it sits above, even after the arithmetic is right.** #195 fixed the shared total's arithmetic; #197 found that five components each held their own `usePartner` state, so the sheet could show an account shared while the Overview behind it still read private and zero. Two copies of one server answer is the same class of bug as two definitions of a lookup, and it had already caused #175 and #177 that week. When more than about three call sites need the same fetched state, the fix is one store, not careful prop passing.
- **Grep the reads before building on a plan that says the reads are safe.** `docs/CUSTOM_CATEGORIES.md` claimed renames were safe because rows point at ids. Rows carried ids and every endpoint still resolved by label, so the first rename would have dropped a member's history into Everything else and split a budget from its own spending. It cost one extra stage (#205) because it was caught by reading the selects before the rename shipped, and it would have cost a member's visible history if it had been caught after.
- **Write the new key before reading it, and keep the old path alive while you compare.** Category ids landed in migration 0024 and nothing read them for a whole stage, on purpose, so id and label could be checked against each other on real data before anything depended on either. The same ordering carried the resolver refactor (#204 changed the seam and not one answer, proved over the whole input domain against a fixture captured from the old module). It is slower and it is the only version of this that cannot move somebody's Score without telling them.
- **A generated file is a fact written twice, and the second copy loses its last line first.** `check-category-ids.ts` exists because migration 0024's mapping cannot import the taxonomy: it is SQL applied by hand, long after the deploy. It earned its place on the first run by catching a generated file that had lost its final entry to a missing newline, which would have left "Transfer in" with a null id forever, on every table.
- **A TDZ error typechecks cleanly and throws on first import.** `BUILTIN_TAXONOMY` was evaluated at module load, before the id helpers it calls were initialized. TypeScript was happy, the build was happy, and the module threw the first time anything imported it. Found by running the check, not by reading it, which is the argument for a script that executes the module over a review that reads it.
- **Unicode names things for archivists, not for people searching.** Searching "coffee" in the emoji picker returned nothing, because Unicode calls that emoji "hot beverage". CLDR's annotations are what every emoji keyboard actually searches, so the generator merges name, subgroup and CLDR keywords, which is the whole difference between a 73KB dataset and a 102KB one. Then "rent" matched "parent" and "transparent", so matching became per word prefix, which keeps "coff" finding coffee and drops the accidents. Both bugs came from using the feature, not from testing it.
- **Ask the machine what it can draw rather than asking a version table.** An emoji newer than the operating system renders as an empty box, and a grid with holes reads as a broken screen rather than as an old computer. Measuring each glyph against the missing-glyph width finds them in 17ms for 1,898 emoji, catches ZWJ sequences that fell apart (measurably wider than one emoji), and needs no table to maintain. Built-in defaults are still capped at Unicode 11.0, because nobody chose those and they have to draw everywhere.
- **A patch that applies half the response leaves the screen half wrong.** After a re-categorization the client applied the new category, group and kind and not the new emoji, so a charge moved to Coffee shops sat there wearing a shopping bag until the next page load. It was introduced the day icons shipped and invisible until somebody picked a category whose icon differed. When a server returns the whole new state of a row, apply the whole thing rather than the fields you were thinking about.
- **An empty thing created on purpose must not be filtered out with the empty things nobody wanted.** The picker drops empty groups so a search does not show bare headers, and a group a member has just created is empty by definition, so creating one looked like it had silently failed with no way to put anything in it. Empty groups are dropped only while searching now. Its sibling in the same PR: the group form offered a Hide that did nothing, since hiding is a leaf-level idea, and a control that is offered and ignored is worse than one that is absent.
- **A backfill that filters with `ilike` has to escape the pattern.** `%` and `_` are wildcards, so a rule made for a merchant like `PAYPAL *INST_XFER` would have matched more than itself, and a rule that files somebody else's charges is worse than one that misses. Escape at the point the pattern is built, and cover it where the matching rules already live.
- **A correction on a settled charge proves nothing about the sync.** A Plaid sync only rewrites transactions returned in `added` or `modified`, so correcting a three-week-old charge and finding it intact tests nothing: it was never touched. The two ways to get a real test are correcting a pending charge and waiting for it to post, or clearing one item's cursor so its history replays through the same upsert (safe, since the upsert dedupes on `plaid_transaction_id`). Written into `docs/PRODUCTION_CHECKS.md` because it is exactly the check somebody would otherwise perform on themselves and believe.
- **A total computed from a different source than the list it sits above will drift, and it can drift all the way to zero.** The shared Overview drew each side's accounts from per-account scopes and then computed the headline figure from a coarse pref and a full-account sum, so the two could never contradict each other loudly enough to be noticed: the list was right, the number was 0, and sharing an account changed the first and not the second. A figure that summarises a list has to be accumulated in the same pass over the same rows with the same skip rule, not derived independently and trusted to agree.
- **A fixture that cannot exhibit the bug will certify the bug.** #188's layout harness used short merchant names, so no row wrapped, so nothing overflowed, so a list that could not overflow passed a test about overflow and shipped a trapped scroll wheel (#189). When measuring a layout, build the fixture from the content that stresses it, the two-line merchant name and the thirteen-account column, not from tidy sample data.
- **Two timestamps on a row can both be wrong for one question.** "How old are these balances" looked answerable from `plaid_items` twice over and was not: `last_synced_at` is written by transactions-sync as well, and the one item that needed the answer syncs transactions perfectly while every balance call times out, so it read as freshly synced forever; `updated_at` is trigger-maintained and moves on any write, including the cursor. A timestamp is only trustworthy for the fact it is written beside. `balances_refreshed_at` is written in exactly one place, next to the snapshot it dates.
- **An early-return flag has to be read from the side you control.** Plaid's Link still hands back a public token in update mode, and exchanging it mints the duplicate item that update mode exists to prevent. The safe read is the repair flag the app put on its own queue, not the metadata coming back from the SDK.
- **A timeout is not a refusal, and treating them alike loses a whole strategy.** `/accounts/balance/get` timing out means the bank is slow; a dead item or a permissions error means the data genuinely is not available. Only the first has a good fallback (`/accounts/get`, Plaid's own cached balance, no round trip to the bank). Collapsing the two would either paper over real errors with stale figures or throw away the one bank that needed the fallback.
- **An empty-state branch can sit above the feature that fills it.** The Plans page returned "No plans yet" on `views.length === 0` before reaching the grid, so the goal cards added in #184 were unreachable for exactly the member they were built for, and the Overview half shipping fine made it look like a partial deploy rather than a bug. When adding a case to a list, check what returns before the list is rendered.
- **A shared frame that replaces children makes its own links unreachable.** `SharedPage` swapped in the blank canvas on every shared route while the space was empty, so following the canvas's "A bill" tile landed on Bills and rendered the canvas again, and the first bill could never be added, since the tab only appears once a bill exists. A frame should own one screen, not override every screen beneath it.
- **A permissive default is a decision nobody made, and it outlives the code that set it.** `share_balances` was `DEFAULT TRUE` in a migration and `true` again in a code default, and a third fallback in `scopeFor` agreed with both, so three independent layers all said "share it" and none of them had ever asked. The product copy said the opposite, in writing, in the same modal that created the partnership. When a default decides who sees somebody else's bank balances, the safe direction is the revoking one, and closing existing rows matters as much as changing the column: the flip alone would have protected only future partnerships.
- **A batch is a barrier, and a barrier is not concurrency.** Slicing items into rounds of six and awaiting each round means round two cannot start until the slowest bank in round one answers, so one twenty-second institution parks five idle workers and leaves six items untouched. The fix that looks done is only half done until the rounds become a pool: workers pulling from one cursor with nothing to wait on. Same shape as any "chunk and `Promise.all`" loop over a slow remote.
- **Budgeting the slow call is not budgeting the work.** `networth-snapshot` stopped starting new items at 18s and was still killed at 25, because the per-item work is a Plaid call plus two Supabase writes and only the Plaid call was inside the budget. A deadline has to reserve for the tail after the thing you were timing.
- **An incremental cursor means a feature added today never reaches yesterday's rows.** Merchant art shipped as a column filled by `/transactions/sync`, which by design never revisits a row, so a member whose history had already synced saw no art at all and would keep seeing none until each merchant charged them again. The general move is a lookup table keyed by the thing the data is a fact about (the merchant), not the row, so one write repairs the whole history without replaying the sync.
- **Returning early is a correctness requirement when the same function also deletes.** A recurring sync that reconciles against Plaid's answer deletes what Plaid no longer returns. Under a permissions error Plaid returns nothing, which is indistinguishable from "nothing recurring any more" if you keep going. The refusal has to short-circuit before the upsert and before the delete, not just be logged more quietly.
- **A card that renders art is not a card that asked for art.** The Overview transactions card showed monograms for weeks after merchant art shipped, and the cause was two layers up: `/api/finances` selected no `logo_url` and did no cache lookup, and the row component was the older `BrandTile`. When one surface disagrees with another about the same data, check what each one actually requested before debugging the renderer.

- **A fixed averaging window over a variable history inflates every ratio built on it.** `_finance-snapshot.ts` divided by a constant 90 days while a member had three weeks of transactions. That did not make the numbers noisy, it made them wrong in a consistent and flattering direction: emergency fund read 3x the months it actually covers, investing pace 3x the pace, debt load a third of the burden. The only figure that survived was savings rate, and only by luck, because it is a ratio of two numbers that were both a third too small. Any "per month" figure must divide by the history that exists, not the window that was requested.
- **A neutral placeholder inside a weighted score is not neutral.** `creditFactor` returned a flat 70 when there was no credit data. That was 10.5 points of a score presented to the member as their own, and because a 70 leaves the most headroom, it won the "biggest lever" ranking, so the app's single loudest instruction was to improve the one thing it had no data about. The fix is to drop an unmeasured component and renormalize the remaining weights, never to fill it in with a plausible number.
- **Reading the sign of a transaction is not reading what happened to the money.** `/api/finances` treated every outflow as spending and every inflow as income, so a transfer to savings, a Venmo to a friend, and a credit-card payment all counted as money spent. The card payment was the worst case and the one nobody spots by eyeballing a total: the purchases it pays for already counted when they happened, so the member was billed twice in the same month for the same coffee. Only the category can tell a card payment from a car payment, and Plaid's *detailed* `personal_finance_category` is the level that carries it (the primary cannot). The blast radius reached past the dashboard, because spending and income feed the Score's savings rate and emergency-fund factor. Anything that classifies money by sign alone is wrong in the same way.
- **One AND-gate over two independent sources withholds both, and a loop that returns on first failure turns one bad item into an outage.** `api/finances.ts` required items AND transactions before returning anything, so real, already-stored balances were queued behind a feed that arrives minutes later and sometimes never. In the same PR: `networth-snapshot.ts` returned 502 the instant one item's balance call failed, and the snapshot rewrite sat inside that loop, so one broken connection meant nothing refreshed at all, while the caller discarded the response body and showed no error. Gate per section, isolate per item, and report what failed.
- **Deleting demo data makes degenerate shapes reachable for the first time.** Removing the mock layer meant `NetWorthChart` could finally receive a one-point series, a dead-flat series, and a negative series; it divided by `series.length - 1` and scaled bounds by 0.985/1.01, so all three produced NaN paths or inverted bounds. The same removal exposed a delta chip hardcoded to "up", safe only while the number came from a demo household that always rose. Seed data is not just wrong content, it is a shape filter hiding the empty and edge cases.
- **Check the account before the config** - a Plaid entitlement that looks inexplicably stuck is more likely the wrong account than a broken setting. Five months of "Production under review" were a different client ID's dashboard. Same shape applies to any per-account SaaS console.
- **Probe env changes without signing in** - `curl -X POST .../api/plaid/link-token -d '{}'` returns 401 when creds are present and 503 when `plaidConfigured()` is false, which distinguishes "Vercel has not picked up the env yet" from "auth is rejecting me" in one call. Plaid's real reason lands in the server log (`[plaid] link/token/create failed`), and the Vercel runtime-log query needs a short `since` window or it times out.
- **Env vars with embedded newlines** — `SUPABASE_ANON_KEY` had a `\n` at position 208 from a copy-paste. Node fetch headers reject CR/LF. `api/_env.ts` strips non-printable chars from all server-side env reads.
- **ES256 vs HS256** — Newer Supabase projects use asymmetric JWT signing keys (ES256). Legacy "JWT Secret" doesn't sign user tokens anymore. `api/_supabase-jwt.ts` checks `header.alg` and routes to JWKS (ES256) or HMAC (HS256) accordingly.
- **GRANT for raw-SQL tables** — Tables created via SQL migration don't auto-grant Data API access. Every new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated;` or every request returns silent 401.
- **Unescaped backticks in template literals** — `BASE` prompt had backticked angle brackets inside a backtick-delimited string. JS parser closed the template early and tried to interpret the rest as tagged template expressions ("X is not a function" at module load). Don't use backticks in prose inside backtick-delimited strings.
- **PostgREST OR filter quirks** — `or=(user_id.eq.X,partner_user_id.eq.X)` returned `[]` even when matching rows existed. Switched to two parallel queries + client-side merge.
- **Double-read of fetch response body** — `/api/plans` GET error path was reading `.text()` after `.json()`; fixed by buffering once and reusing.
